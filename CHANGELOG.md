## 2026-09-22 — подтверждение кампаний в отчётах по трафику

Сборщик больше не требует доступности Campaigns.get для каждой кампании,
если запрашиваются только показы, клики и расход (`measurement=null`).
Отсутствующие ID подтверждаются отдельным CAMPAIGN_PERFORMANCE_REPORT того же
клиента и периода; его полные итоги сверяются с дневными строками. Исходный TSV,
параметры и SHA-256 сохраняются в приватном состоянии отчёта. Неполная/повторная
выборка настроек, неподтверждённые ID, ошибка API и расхождение итогов блокируют
новую версию. Настройки, цели и атрибуция не выдумываются; ограничение явно видно
в отчёте. Для конверсий проверка настроек всех кампаний остаётся обязательной.
Строки объявлений с недоступным ID (`--`) сохраняются в статистике;
получение текущего текста выполняется только для реальных ID объявлений.

Даты статистики Reports относятся к Москве; TimeZone кампании задаёт расписание
показов и не запрещает сбор при другом часовом поясе. Источник:
https://yandex.com/support/direct/ru/troubleshooting/shows .

После переподключения `direct_runtime.features` содержит
`traffic_reports_campaign_identity` и `reports_moscow_statistics_timezone`.
Если `restart_required=true`, используйте новый процесс MCP; не считайте
изменение исходников обновлением уже подключённого процесса.

## 2026-09-21 — длительная проверка посадочных

Для `direct_campaign_repair` с `new_groups` preview выполняется в фоне.
Ответ `running` содержит `job_id`; `direct_write_job` возвращает итоговый preview
с артефактом и одноразовым токеном, связанным с полным live preflight. Ошибка
проверки не выдаёт токен; apply по-прежнему требует MCP elicitation и повторно
читает состояние кабинета. Запись не запускается из preview.

HTTP-проверка не загружает повторно одну страницу для разных `#якорей`:
все исходные ссылки остаются в результате, а якоря проверяются в браузере.
Разные query-параметры и устройства проверяются отдельно. Кеш ограничен точным
планом и 15 минутами; для новых групп он теперь действует и между preview/apply.
Сетевой тайм-аут составляет 20 секунд; общий бюджет страницы учитывает очередь
из шести запросов к одному хосту. Непроверенные URL остаются BLOCK.

## 2026-09-21 — группы в существующей поисковой кампании

`direct_campaign_repair` принимает `campaigns[].name` для переименования и
`new_groups` с `semantic_plan` для добавления поисковых групп, ResponsiveAd,
ключей и автотаргетинга в существующую остановленную ЕПК. Бюджет и стратегия
не меняются. Новая кампания, импорт XLSX и повторное создание прежних групп
не требуются. Поддержка добавления ограничена текстовым Поиском без РСЯ.

Сохраняются live preflight, неизменный SHA-256, одноразовое подтверждение,
MCP elicitation, журнал, остановка при частичной ошибке и независимый readback.
Проверяются принадлежность объектов, полная выборка, дубли групп/ключей,
география, семантика, дополнения и конечные URL. Повторная проверка job
использует сохранённые ID; неизвестный исход не разрешает повторный add.
Для активации требуется переподключение MCP. `direct_runtime` покажет
`protocol_revision=2026-09-21-search-append-v1` и
`existing_search_groups_append` в `features`.

- `direct_regions` — справочник регионов Директа (`dictionaries.get`, `GeoRegions`): поиск кода по названию и обратная проверка готовых кодов. Директ коды не валидирует, поэтому неверный `geo_ids` или `RegionIds` не вызывает ошибку, а молча даёт данные и показы по другому региону; коды, которых нет в справочнике, теперь возвращаются списком `unknown_ids`. Совпадения приходят с путём до корня — «Москва» это и город `213`, и «Москва и область» `1`. Справочник загружается один раз на процесс, целиком в контекст не выгружается.
- `direct_account_settings` — настройки кабинета, которых нет в Reports API: корректировки ставок (`bidmodifiers.get`), условия ретаргетинга (`retargetinglists.get`) и общие наборы минус-фраз (`negativekeywordsharedsets.get`). Отчёт показывает статистику по срезам `Device`, `Gender`, `Age`, но не выставленный коэффициент, а «нет мобильных конверсий» и «на мобильные стоит −100%» — разные диагнозы. Секции читаются независимо: ошибка одной приходит полем `error` внутри неё. Список кампаний режется на пачки по 10, как требует `bidmodifiers.get`, а усечение выборки больше 50 кампаний отмечается полем `truncated`.
- `direct_ads` — объявления и посадочные страницы (`ads.get`). Ссылки нет ни в одном типе отчёта: поле `Href` живёт только здесь, и запрос его в Reports API отваливается с `error_code=8000`. Кроме списка объявлений тул сразу отдаёт сводку `landing_pages` — уникальные URL, число объявлений на каждом, кампании и разобранные UTM, — потому что чаще всего нужен именно ответ «одна ли это главная на весь аккаунт и размечены ли ссылки». Пустой `SelectionCriteria` метод не принимает, поэтому без явной выборки сначала читаются кампании клиента, а `CampaignIds` уходят пачками по 10. Архивные отсеиваются по полю `State` в ответе, а не через критерий: неверное значение перечисления стоило бы 20 баллов и целый вызов. Запрашивается блок `TextAd` — у графических, видео и смарт-объявлений `href` придёт пустым, их число видно в `ads_without_href`.
- `direct_wordstat` — частотность Яндекс Вордстата: спрос по фразе, вложенные и похожие запросы. До 50 фраз за вызов, фильтр по минимальной частотности, регионы Директа. Полный список сохраняется тем же TSV, что и отчёты, и читается через `direct_read_report`; в ответ уходит сводка по каждой фразе. Метод живёт в устаревшем API v4 — аналога в v5 нет, — поэтому недоступен в песочнице, а баллы v4 в поле `units` не попадают. Отчёты Вордстата удаляются из очереди аккаунта сразу после выгрузки, в том числе когда вызов упал.
- База знаний по Яндекс Директу как MCP-ресурсы: оглавление `direct://kb` и 13 документов `direct://kb/<имя>` — политика, миграция, чек-лист запуска, технические лимиты, контракт API, стратегии, цели, фразы, таргетинги, донастройка, рецепты отчётов и границы сервера. Источники: официальная справка Директа и документация API, материалы eLama, публичная практика агентств.
- Инструкции сервера называют правила, нарушение которых не даёт ошибки API и потому проходит незамеченным: микроединицы в денежных полях, обязательный автотаргетинг в поисковой группе, лимиты текстов до вызова.
- `YD_DEFAULT_WEEKLY_BUDGET` — недельный бюджет кампании по умолчанию; попадает в инструкции, чтобы не проговаривать одну и ту же сумму на каждом запуске.

### Fixed

- Политика 1.3.0 отменяет требование отключать расширенный геотаргетинг по
  [обновлению Яндекса от 31.08.2026](https://b2b.yandex.ru/adv/news/obnovlenie-geotargetinga-v-direkte).
  Компилятор не требует ручного подтверждения, аудит не оценивает legacy-поле
  `ENABLE_AREA_OF_INTEREST_TARGETING`, отчёт не показывает его как доступную
  настройку. Старые входные поля принимаются без влияния на план; проверка
  регионов групп остаётся обязательной.

- Клиентский HTML показывает только созданные объекты и настройки; сравнение
  плана с фактом и расхождения остаются во внутреннем JSON-аудите.
- Ремонт комбинаторных объявлений передаёт уточнения в форме `CalloutSetting`
  с `SET`, которую требует `Ads.update`; add-only поле `AdExtensionIds` больше
  не используется при обновлении.
- Новые объявления ЕПК компилируются как `ResponsiveAd`, потому что создание
  `TextAd` в ЕПК больше не поддерживается. `direct_ads` читает оба типа через
  v501 и использует корректное поле `AdExtensions` вместо add-only
  `AdExtensionIds`.
- Оба пути создания объявлений требуют нативный `ResponsiveAd` с 3–7
  уникальными заголовками и ровно 3 уникальными текстами. Legacy
  `direct_campaign_setup` отклоняет `TextAd` до preview и вызывает `Ads.add`
  через v501.
- Reports переведён на `/json/v501/reports`; добавлена локальная проверка типов
  отчёта, полей, фильтров, сортировки, лимитов, несовместимостей и актуальных
  моделей атрибуции до расходования API-баллов.
- Из `TextCampaignFieldNames` удалён отсутствующий в актуальной v501 схеме
  `TrackingParams`, а для `UnifiedCampaignFieldNames` добавлен
  `NegativeKeywordSharedSetIds`.
- `TrackingParams` нового bundle отправляется как строка GET-параметров без
  начального `?`, как требует контракт кампании.
- Локальная валидация создания синхронизирована с ограничениями API: кампании
  отправляются пачками по 10, проверяются имена до 255 символов, минус-фразы,
  `DisplayUrlPath`, лимит узких символов в текстах и зависимость полей от
  `Href`; `ResponsiveAd` поддерживает посадку только на `BusinessId`.
- `StartDate` кампании сверяется с московской датой, а не с датой машины, где запущен сервер. Для кабинета восточнее или западнее Москвы проверка «не в прошлом» ошибалась ровно на сутки и отвергала валидный план (или пропускала невалидный).
- Набор правил ruff зафиксирован в `pyproject.toml` явным `select`, а версия линтера ограничена сверху. Раньше набор брался из дефолта ruff, дефолт расширился в новой версии — и lint-шаг CI покраснел на 17 замечаниях без единого изменения в коде.
- Запуск `python -m yadirect_mcp` — команда из всех примеров подключения падала с `cannot be directly executed`, потому что в пакете не было `__main__.py`.
- Отчёт больше не теряется, если в TSV попалась строка с лишним разделителем: файл сохраняется до разбора, а ошибка возвращается полем `parse_error`.
- Итоги по отчётам с целями Метрики: колонки вида `Conversions_<цель>_<атрибуция>` больше не выпадают из `totals`, производные метрики пересчитываются по каждой цели.
- Поллинг офлайн-отчёта переживает нечисловой заголовок `retryIn` вместо аварийного завершения.
- Ответы `502`, `503` и `504` от балансировщика повторяются, а не отбрасывают уже поставленный в очередь отчёт.
- Частичное создание объектов кампании: ID из успешных пакетов сохраняются в ответе, если следующий пакет упал.
- Выгруженный TSV записывается байт в байт как пришёл от API, без подстановки CRLF на Windows.

## 2026-09-24 — каталог ретаргетинга
Read-only MCP-инструмент direct_retargeting_catalog читает доступные одному
клиенту цели и сегменты через официальный Live4 GetRetargetingGoals.
Обычный direct_goal_catalog для целей оптимизации сохраняет прежний контракт.
Проверки логина, полноты, дублей и принадлежности данных не пропускаются.
Предпроверка retargeting_rules использует этот каталог и проверяет также
служебную цель «посетил сайт» с заданным сроком. Типы segment/audience_segment
с параметром days отклоняются: API игнорирует этот период для сегментов.
Запись, проверка принадлежности кампании и независимый readback сохранены.
Для сегментов добавлен явный аргумент {"segment_id": ID} внутри
retargeting_rules[].goals[] без days. Live-каталог проверяет тип segment или
audience_segment; для goal_id+days допускаются только цели. Сервер не обещает
временной диапазон сегмента, которым API управлять не позволяет.


### Привязка существующего сегмента через repair
direct_campaign_repair принимает отдельный пакет audience_link с точными
ad_group_id, retargeting_list_id, segment_id. Только остановленная сетевая ЕПК,
один доступный сегмент Метрики, точное правило ANY, без существующих аудиторий
и без активных ключей/автотаргетинга. Иные изменения в том же пакете запрещены.
Хеш связывает все ID; grant связывает live-снимок. Перед единственным
AudienceTargets.add снимок повторно сравнивается. Общая блокировка логина,
одноразовое подтверждение, журнал запроса/ответа и readback сохраняются.
Повтор после неизвестного результата, замена условий и запуск не допускаются.


### 25.09.2026 — отдельная группа сегмента в существующей РСЯ
direct_campaign_repair принимает отдельный audience_group: campaign_id, source_ad_id, segment_id, name. Создаёт одну группу на выбранный доступный сегмент и клонирует принадлежащее кампании ResponsiveAd. Кампания может быть включена: бюджет, стратегия, состояние и прежние объекты сохраняются; новое объявление остаётся черновиком. Нет вызовов moderation/resume. Дубли, неполные выборки, чужие объекты и изменения после preview блокируют запись. Любой частичный add сохраняется в журнале и не повторяется. Автотаргетинг новой группы отключается до создания объявления; readback проверяет точное условие сегмента и сохранность прежних объектов. Кнопка и карусель требуют отдельной проверки интерфейса.
