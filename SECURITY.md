# Политика безопасности

## Поддерживаемые версии

| Версия | Поддержка |
|---|---|
| 0.2.x | Да |
| 0.1.x | Только критические исправления |

## Как сообщить об уязвимости

Не создавайте публичный issue для уязвимости, которая может раскрыть OAuth-токены, получить доступ к чужому кабинету или выполнить рекламную операцию без подтверждения.

Используйте **Security → Report a vulnerability** в GitHub-репозитории и приложите:

- затронутую версию;
- сценарий атаки и влияние;
- минимальные шаги воспроизведения;
- безопасный proof of concept без реальных токенов и клиентских данных;
- предложение по исправлению, если оно есть.

## Границы безопасности

- Сервер рассчитан на локальный stdio-транспорт и доверенный MCP-клиент.
- `YD_TOKEN` является секретом и не должен храниться в Git.
- `YD_ALLOWED_LOGINS` — дополнительная защита от ошибочного кабинета, но не замена правам Яндекс Директа.
- `YD_MODE=campaign_setup` разрешает реальные write-запросы после подтверждения.
- Подтверждение одноразовое, действует 30 минут и связано с логином и SHA-256
  точного нормализованного плана; строка из другого preview не принимается.
- Фраза возвращается MCP-клиенту и модели. Это защита от повторного применения,
  неверного кабинета и изменения плана, **не доказательство согласия человека**.
  При автоматическом одобрении вызовов клиентом модель технически может выполнить
  preview и apply подряд. Для обязательного участия человека подтверждение
  write-тулов должен обеспечивать доверенный MCP-клиент вне контроля модели.
  Перенос фразы в stderr или доступный модели файл такой гарантии не создаёт.
- Write-путь создания — типизированный `direct_campaign_apply`; legacy raw-инструмент
  удалён из MCP. `direct_campaign_plan` доступен только в режиме настройки.
- Создание кампании не атомарно; частичный результат требует ручной проверки.
- Проект не запускает показы автоматически и делает независимый readback.
- `YD_CREATE_REPORT_SSH_HOST` вместе с явно заданными
  `YD_CREATE_REPORT_REMOTE_ROOT` и `YD_CREATE_REPORT_PUBLIC_BASE_URL`
  включает публикацию коммерческих настроек и
  семантики по предсказуемому URL `/elama/<client_login>/create/`. `noindex`
  снижает вероятность индексации, но не заменяет аутентификацию; без этой
  переменной итоговый HTML остаётся только в `YD_OUT_DIR`.
- Публикация выполняет SSH/SCP под пользователем настроенного SSH-алиаса. Root
  не требуется: используйте отдельную учётную запись с записью только в каталог
  отчётов и чтением файлов веб-сервером. Сервер задаёт режимы 0755/0644, сохраняет
  предыдущий HTML и заменяет файл атомарно; владельца через `chown` не меняет.
- Проверка посадочных допускает HTTP(S) без userinfo, проверяет все DNS-адреса
  и каждый редирект, соединяется с проверенным публичным IP с исходными Host/SNI.
  Приватные, link-local, loopback и multicast адреса запрещены; прокси из окружения
  отключены. До 30 страниц, 6 соединений, 5 редиректов, 12 секунд на страницу и
  40 секунд на всю пачку. HTML ограничен 2 МБ после распаковки gzip/deflate. Один запрос на хост
  с интервалом 0,5 с; Retry-After для 429/503 останавливает повторные запросы.
- `direct_campaign_plan` помечен `readOnlyHint=false`, `destructiveHint=false`;
  он может сохранять локальный JSON, но не удаляет данные и не вызывает API.
  Остальные аннотации учитывают локальную запись артефактов. Аннотации MCP описательные
  и не являются разграничением доступа. JSON/TSV-читатели ограничены `YD_OUT_DIR`;
  этот каталог должен содержать только предназначенные клиенту данные.
- Готовые TSV, журналы применения и резервные копии не удаляются автоматически.
  Очистка старых JSON-планов/аудитов: `python -m yadirect_mcp.cleanup ./out` показывает
  список; только `--apply` удаляет файлы. По умолчанию сохраняются последние 100,
  удаление допустимо лишь для файлов старше 30 дней; подкаталоги не обходятся.

## Публичные отчёты и резервные копии

Публикуемый HTML не имеет встроенной авторизации. Любой, кто знает или угадает
URL, может прочитать структуру, бюджеты, цели и семантику. Включайте публикацию
только для данных, разрешённых к такому размещению; для закрытых отчётов нужна
аутентификация на веб-сервере. `noindex` и сложное имя каталога не ограничивают доступ.

Файлы `index.html.backup-<stamp>` также могут обслуживаться веб-сервером по URL.
Встроенная очистка намеренно их не удаляет: резервные копии обеспечивают откат,
автоматической ротации нет. Владелец хостинга задаёт закрытое хранение резервных
копий, запрет их HTTP-выдачи и срок хранения. Изменения конфигурации хостинга
не выполняются инструментом создания кампаний.

Загрузка `images` в `direct_ad_assets_create` читает явно указанный локальный
файл PNG/JPG/GIF либо base64. Preview показывает имя, размер и SHA-256; токен
подтверждения привязан к фактическим байтам. Изменённый файл требует нового preview.

## Журнал и согласие на запись (11.09.2026)

Для записи необходим MCP 1.29+ и поддержка elicitation в клиенте. Сам токен
confirmation согласия не доказывает. Журнал фиксирует клиента (`client_attested`),
а не независимо аутентифицированного человека; доверенный клиент должен показывать
запрос пользователю и не разрешать модели отвечать за него.

`decline`, `cancel`, отсутствие поддержки form elicitation и принятая форма без
`approve=true` имеют разные коды ошибок. Никакой из этих ответов не разрешает запись;
сервер не подменяет их согласием и не переходит на незащищённый write-путь.
Отмена/отказ не расходуют preview-токен: новый вызов снова требует согласия клиента.
Токен резервируется на время показа формы; параллельный запрос с ним отклоняется.
Перед записью повторно проверяются срок, логин и хеш, затем токен расходуется.
Это позволяет исправить клиентский показ формы без повторного дорогого preflight,
пока действует токен. Перезапуск MCP по-прежнему аннулирует все токены в памяти.

Фоновые операции сохраняют запрос перед отправкой и ответ до следующего этапа.
Журнал `YD_OUT_DIR/jobs/<job_id>.json` и `login-<sha256>.lock` переживают отмену
ожидания и перезапуск. API add/update автоматически не повторяются. Если исход
неизвестен, сверочное чтение показывает кандидатов, но не объявляет их доказанным
результатом. Оператор проверяет состояние процесса, журнал, все затронутые объекты
и отсутствие незавершённого запроса. Только затем допустимо вручную снять точную
блокировку логина; журнал сохраняется. Повтор того же отправленного плана возвращает
исходный job, поэтому оставшиеся действия готовят отдельным проверенным планом.
Не удаляйте журнал для повторного запуска всей операции.

Секреты дополнительных API (`YD_WORDSTAT_TOKEN`, `YD_METRIKA_TOKEN`) передаются
только окружением. FastMCP не загружает `.env` из рабочего каталога.


## Восстановление публикации и эксплуатация

`direct_publish_job` записывает только существующий HTML в настроенное место
публикации; не создаёт рекламный API-клиент и не принимает произвольный удалённый
путь. Источник ограничен HTML исходного apply job внутри YD_OUT_DIR. Preview связывает
логин, исходный журнал, SHA-256 байтов и конфигурацию назначения; apply требует
одноразовый токен и MCP elicitation. Перед публикацией выполняется повторная сверка
под общей блокировкой логина; публикуется отдельный снимок. Журнал дочерней операции
сохраняет запрос до внешнего вызова; отмена/неизвестный исход не разрешают повтор.
Ошибочный публичный readback не считается успешной публикацией. Смена HTML,
исходного журнала или назначения требует нового preview. Автоматического повтора нет.

`direct_runtime` возвращает только перечисленные диагностические поля; окружение,
токены и секреты не включаются. `direct_pending_actions` требует конкретный разрешённый
логин и читает локальные журналы; повреждения обозначаются неполнотой реестра.
Эти инструменты не снимают блокировки и не подтверждают UI-действия или запуск.


Товарные URL-фиды создаются только в campaign_setup: точные имя, URL и логин
входят в SHA-256 и preview; elicitation, одноразовый токен, повторный preflight,
блокировка клиента и durable job обязательны. Дубли и неполное чтение блокируют
запись; неизвестный исход не повторяется. Непубличные адреса отклоняются.
После успешного add ID сохраняется даже при сбое проверки. DONE с непустым
каталогом и PROCESSED у объявления проверяются отдельно от факта создания фида.
Источник по сайту создаётся через интерфейс; соответствие его URL и FeedId
подтверждает специалист, доступность фида и разметку проверяет MCP. Это явно
обозначено как caller_reviewed, а не независимое доказательство API.
