# Параметры инструментов

## Выбор бизнес-профиля

В typed bundle поддержаны `policy_name` и `profile_context`. Без policy_name
сохраняется agency_default_v1 1.12.0 и прежний plan_hash. Шесть v1, два e-commerce v2 и
полный контракт истории: `direct://kb/policy-profiles`.
`direct_policy(policy_name=...)` возвращает policy, available_profiles и
planning_defaults: текущий состав стартового теста, ориентир 30 000 RUB в месяц
и границы автоматизации. planning_defaults не входит в снимок policy и не
добавляет кампании в bundle. `channels.product` в e-commerce v2 поддерживает
ShoppingAd/ListingAd и общий бюджет галереи/сетей. `direct_product_source`
читает/проверяет источник, `direct_feed_create` создаёт URL-фид через preview/apply.
Источник по сайту с разметкой сначала создаётся в интерфейсе Директа; далее
нужен доступный API FeedId. Контракт полей: `direct://kb/product-campaigns`.
`direct_campaign_audit(policy_name=...)` применяет выбранные правила;
после создания readback берёт профиль из исходного плана автоматически.
В новом плане сохраняются policy_snapshot, policy_fingerprint, profile_context,
profile_office, profile_decisions; они входят в SHA-256 и не являются полями API.

## Поля нового bundle — политика 1.12.0

`tracking_profile` по умолчанию `utm_v1`: все параметры `regulation_v1` плюс
`utm_source=yandex`, `utm_medium=cpc`, `utm_campaign={campaign_id}`,
`utm_content={ad_id}`, `utm_term={phrase_id}`. Legacy-профиль задаётся явно.
`settings.ALTERNATIVE_TEXTS_ENABLED` по умолчанию false; true включает автотексты.

```json
{
  "client_budget": {
    "amount": 30000, "period": "monthly", "currency": "RUB", "includes_vat": false
  },
  "business_profiles": [{
    "business_id": "123456789", "phone": "+74951234567",
    "address": "Москва, Тестовая улица, 1", "has_office": true
  }]
}
```

В примере сумма без НДС; для клиента основу суммы фиксируют явно.
Это фрагмент исходного bundle. `client_budget` — общий лимит только кампаний
плана, включая геоварианты; `weekly_budget` по кампаниям заполняется отдельно.
Для includes_vat=true обязателен vat_percent. Значения конечные и положительные,
amount имеет точность не более микроединицы. При period=monthly сумма без НДС
умножается на 12/52 и округляется вниз до микроединицы; это не календарный
месячный лимит. Превышение лимита и несовпадение валюты блокируют запись.
`summary.client_budget` показывает лимит, сумму, остаток и scope=planned_campaigns.
Пропуск поля в старых данных даёт not_configured, а не PASS.

`business_profiles` обязателен для всех BusinessId нового bundle, по одному
профилю на ID без лишних и дубликатов. phone — один телефон без добавочного,
address — строка или null (null допустим лишь без офиса), has_office — boolean.
Нормализация убирает оформление телефона, заменяет российский префикс 8 на 7,
у адреса сравнивает регистр и пробелы. Нечётких смысловых совпадений нет.
Ожидаемые данные берутся из согласованных контактов клиента. Preflight и readback
перечитывают Phone/Address/HasOffice/IsPublished через Businesses.get.

Для maximum_conversion_rate `strategy.goal_id` — реальная цель из priority_goals
или 13 (все ключевые цели). Для 13 требуется хотя бы одна приоритетная цель
кроме системной 12; сам 13 запрещён в priority_goals. Проверки счётчика,
выбора целей и каталога сохранены. Все новые поля включены в SHA-256 плана.

## Подготовка и применение после аудита 11.09.2026

Недостающие сведения, включая бюджет, выяснить в начале задачи. Затем
самостоятельно подготовить и проверить полный план и назначение отчёта.
Перед записью MCP-клиент запрашивает согласие через elicitation на конкретный
логин и полный хеш плана. `confirmation` остаётся техническим одноразовым токеном
целостности и сам по себе не разрешает запись. Решение, хеш, время и имя клиента
сохраняются в журнале. Участие человека обеспечивает доверенный интерфейс клиента;
сервер фиксирует `client_attested`, а не удостоверенную личность человека.

Запуск и возобновление показов требуют отдельной явной команды пользователя.
Preview, live preflight, независимый readback, резервные копии и проверки
публикации сохраняются. `BLOCK`, неполные выборки и дубли останавливают запись.
Разрешения среды исполнения и границы доступа это правило не изменяет.

Подробности ниже дополняют краткие описания тулов. Режим report не предоставляет
методы записи в рекламу; локальные выгрузки и сборка HTML доступны.

## direct_client_report

Сбор статистики и HTML кодом, компактная сводка для ИИ. Действия: `initialize`
(проверенная модель и конфигурация), `update` (API и локальная сборка), `brief`
(без API), `write_insight` (вывод по версии данных). Схема, CLI и ограничения:
`direct://kb/client-report`. Не публикует HTML и не вызывает LLM API.

## direct_policy

Машиночитаемая версия регламента и модель статусов аудита.

Ничего не читает и не меняет в кабинете. Возвращает требования к каналам,
бюджету, стратегии, TrackingParams и сведения о внешних списках.

## direct_campaign_plan

Скомпилировать типизированный план отдельных Search/РСЯ/Карт в v501.

Инструмент не вызывает методы записи. Он применяет policy
agency_default_v1, подбирает минус-фразы через negative_keyword_policy, профиль
TrackingParams, безопасные стратегии, прогноз баллов write-фазы и
возвращает сводку с plan_hash и artifact_path. Для одинакового контента нескольких кампаний
используйте campaign_template + campaign_variants; варианты могут менять
только канал, название, географию, бюджет и стратегию.
Каждое объявление принимает только массивы из 3–7 уникальных titles и ровно
3 уникальных texts; одиночные title/title2/text отклоняются до preview.
Нужны semantic_plan и semantic каждой группы; дополнительные объявления
требуют отдельных hypothesis. Схема: direct://kb/structure-semantics.

## direct_list_clients

Список клиентских логинов агентства с валютой и остатком средств.

Отсюда берётся client_login для остальных тулов. Вызывается без
заголовка Client-Login — это агентский метод.

## direct_campaigns

Кампании клиента: id, имя, тип, статус. Нужен для маппинга CampaignId → имя
и чтобы понять, какие кампании вообще стоит тянуть в отчёт.

## direct_campaign_settings

Полные настройки TextCampaign и UnifiedCampaign через API v501.

Возвращает раздельные стратегии Search/Network, места показов, недельные и
дневные бюджеты, настройки геотаргетинга, счётчики и приоритетные цели,
TrackingParams, минус-фразы и исключённые площадки. Метод только читает.

## direct_campaign_audit

Проверить кампании по регламенту, не меняя настройки Директа.

Для каждой проверки возвращает PASS, WARNING, BLOCK или MANUAL и факты,
на которых основан вывод. При include_landing_pages объединяет параметры
Href объявлений и кампанийные TrackingParams. По умолчанию сохраняет полный
JSON-аудит в YD_OUT_DIR; запись локального артефакта не меняет кабинет.

## direct_adgroups

Группы объявлений через API v501: регионы, статусы и параметры URL.

Без фильтров читает группы первых 50 неархивных кампаний и явно сообщает
об усечении. CampaignIds автоматически делятся на разрешённые пачки по 10.

## direct_goal_catalog

ID и названия целей Метрики, доступных выбранной кампании.

Сначала через v501 проверяет, что кампания принадлежит client_login, затем
вызывает официальный GetStatGoals API v4. Цвет и новизна цели этим методом
не возвращаются и остаются ручной проверкой.

## direct_regions

Коды регионов Директа по названию и обратная проверка готовых кодов.

Вызывать всегда, когда в geo_ids (direct_wordstat) или RegionIds
(direct_campaign_plan/apply или legacy setup) уходит регион: Директ коды НЕ
проверяет. Неверный
код не вызовет ошибку — он молча даст данные и показы не по тому региону,
и заметно это станет только по статистике.

query: часть названия, например "Москва", "Ростов", "Татарстан". Регистр и
    «ё» не важны. Совпадения возвращаются с путём до корня (path), потому
    что названия неуникальны: «Москва» — это и город 213, и «Москва и
    область» 1.
ids: коды для обратной проверки. Вернёт названия, а отсутствующие в
    справочнике коды — отдельным списком unknown_ids.
client_login: нужен только агентскому токену — Директ требует заголовок
    Client-Login на клиентских методах. Подойдёт любой логин из
    direct_list_clients.
limit: сколько совпадений вернуть, 1–200.

Нужен хотя бы один из query / ids: справочник целиком тул не отдаёт.
Загружается он один раз на процесс, повторные вызовы баллов не тратят.

## direct_account_settings

Настройки кабинета, которых нет в отчётах: корректировки ставок, условия
ретаргетинга, общие наборы минус-фраз.

Нужен при разборе «почему кампания не работает» и перед выводами по срезам
отчёта. Reports API покажет статистику по Device, Gender, Age, но не
покажет выставленный коэффициент, а это разные диагнозы: «нет мобильных
конверсий» и «на мобильные стоит −100%».

sections: какие секции читать. Доступны bid_modifiers, retargeting_lists,
    negative_keyword_sets. Пусто — все три.
campaign_ids: для каких кампаний смотреть корректировки. Пусто — сервер
    сам возьмёт неархивные кампании клиента, но не более 50; если их
    больше, в ответе будет truncated и число пропущенных.

Секции независимы: ошибка в одной приходит полем error внутри неё, а
остальные возвращаются как есть. Корректировки перемножаются между собой —
как их читать, описано в direct://kb/targeting-adjustments.

## direct_ads

Объявления и посадочные страницы: куда ведёт реклама, что в заголовках,
размечены ли ссылки UTM.

Ссылки в отчётах не существует ни в одном типе: поле Href есть только
здесь. Вызывать, когда разбор дошёл до вопросов «на какую страницу идёт
группа», «одна ли это главная на весь аккаунт», «есть ли метки» — и перед
любыми выводами про конверсию, потому что дорогой клик на нерелевантной
странице выглядит в отчёте так же, как дорогой клик вообще.

campaign_ids / ad_group_ids / ad_ids: чем сузить выборку. Пусто — все
    объявления клиента.
include_archived: включить архивные, по умолчанию нет.
limit: сколько объявлений забрать за вызов, 1–10000.

В ответе landing_pages — сводка по уникальным URL с числом объявлений,
кампаниями и разобранными UTM; domains — домены, на которые идёт реклама.
Запрашиваются TextAd и актуальный для ЕПК ResponsiveAd. У графических,
видео и смарт-объявлений href может прийти пустым; их число видно в
ads_without_href.

## direct_keywords

Ключевые фразы и полные настройки автотаргетинга через API v501.

Нужен для аудита семантики и проверки того, какие категории и варианты
брендовости реально включил Директ. Требуется хотя бы один фильтр.

## direct_report

Выгрузить статистику через Reports API. Пишет TSV на диск, возвращает
путь + итоги + первые строки.

client_login: клиентский логин (см. direct_list_clients)
date_from / date_to: YYYY-MM-DD. Статистика доступна за 3 последних года.
fields: колонки отчёта, например ["Date","CampaignName","Impressions","Clicks","Cost"].
    Набор допустимых полей зависит от report_type. Внимание: поля разных
    классов — сегмент (даёт группировку), метрика, атрибут, фильтр
    (используется только в filters и в отчёт не выводится, напр. Keyword).
report_type: CUSTOM_REPORT (самый общий, по умолчанию) | ACCOUNT_PERFORMANCE_REPORT |
    CAMPAIGN_PERFORMANCE_REPORT | ADGROUP_PERFORMANCE_REPORT | AD_PERFORMANCE_REPORT |
    CRITERIA_PERFORMANCE_REPORT | SEARCH_QUERY_PERFORMANCE_REPORT |
    REACH_AND_FREQUENCY_PERFORMANCE_REPORT
goals: до 10 ID целей Метрики. Для конверсионных полей без явных goals
    MCP читает цели стратегии/приоритетные цели кампаний.
attribution_models: FCCD | LC | LSCCD | AUTO. Явно задаются вместе с goals.
    По умолчанию MCP читает модель кампании, не подставляет LC.
    При разных настройках разделите кампании фильтром CampaignId IN либо
    явно задайте goals и attribution_models для общего сравнения.
conversion_scope: campaign (по умолчанию) согласует цели и модель с кампанией;
    all_goals явно запрашивает агрегат всех целей с LC по умолчанию API.
    Агрегат не является числом заявок. Метаданные сохраняются рядом с TSV.
filters: [{"Field":"CampaignId","Operator":"IN","Values":["123","456"]}]
order_by: [{"Field":"Cost","SortOrder":"DESCENDING"}]
limit: ограничение строк, от 1 до 1 000 000. Сортировка необязательна.
include_vat: суммы с НДС (True) или без (False).

## direct_read_report

Постранично прочитать уже выгруженный отчёт по пути из direct_report.
Без повторного обращения к API и без расхода баллов.

## direct_wordstat

Частотность Вордстата: сколько раз за месяц искали фразу, что искали
вместе с ней и что искали похожего. Пишет полный список на диск, возвращает
сводку по каждой запрошенной фразе.

Нужен на сборке семантики (что брать в кампанию, где спрос есть, а где нет),
на разборе «мало показов» и когда в отчёте надо отделить падение спроса от
падения кампании.

phrases: до 50 фраз за вызов. Операторы Директа работают: «!» фиксирует
    словоформу, кавычки ограничивают фразу, «+» держит стоп-слово.
geo_ids: регионы Директа, например [225] — Россия, [213] — Москва. Пусто —
    без ограничения по региону. Директ коды не проверяет: неверный код
    молча вернёт данные не по тому региону.
min_shows: отбросить подсказки с частотностью ниже порога.
top: сколько подсказок каждого вида показать в ответе, 1–100.

client_login не нужен: данные Вордстата общие для всех кабинетов. Значение
Shows — спрос в поиске за месяц, а не прогноз показов кампании. В песочнице
метод недоступен.

## direct_campaign_apply

Preview или guarded apply типизированного UnifiedCampaign-плана.

Без confirmation компилирует план, выполняет live preflight и выдаёт
одноразовую фразу, привязанную к логину и plan_hash на 30 минут. Повторный
вызов с неизменным bundle и точной фразой создаёт объекты через v501.
Показы не запускаются. Полный результат всегда сохраняется в YD_OUT_DIR.
Итоговый HTML содержит кампании, настройки, группы, таргетинги, ключевые
фразы и объявления; при настроенном SSH публикуется в клиентский /create/.

## Миграция legacy

`direct_campaign_setup` удалён. Используйте `direct_campaign_plan` и
`direct_campaign_apply`, доступные только в `YD_MODE=campaign_setup`.

## Дополнительные поля bundle и проверка полноты

- `time_zone` — имя из `Dictionaries.TimeZones`, по умолчанию `Europe/Moscow`.
  Указывается в payload каждой кампании и сводке; нестандартное значение проверяет preflight.
  Часы расписания относятся к этому поясу, а даты старта/окончания API — к Москве.
- `schedule.holidays` — явное исключение для праздников: `{"suspend": true}`
  либо `{"suspend": false, "start_hour": 9, "end_hour": 18, "bid_percent": 100}`.
  Без него используется обычное расписание по дням недели. Праздничную остановку
  можно задать и при круглосуточном расписании.
- `settings` — объект с булевыми значениями для `ADD_METRICA_TAG`,
  `ENABLE_SITE_MONITORING`, `CAMPAIGN_EXACT_PHRASE_MATCHING_ENABLED`,
  `ALTERNATIVE_TEXTS_ENABLED`, `ENABLE_COMPANY_INFO`, `REQUIRE_SERVICING`.
- `attribution_model` — `AUTO` (по умолчанию), `FCCD`, `LC`, `LSCCD`.
- `channels.<канал>.strategy.bid_ceiling` — предельная ставка в обычных единицах валюты.
- `ads[].age_label` — самостоятельная маркировка `AGE_0`, `AGE_6`, `AGE_12`,
  `AGE_16`, `AGE_18` или `MONTHS_1`…`MONTHS_12`. `age_min` её не подменяет.
- Для нескольких вариантов одного канала каждому нужен явный `weekly_budget`
  (может быть задан в общем `campaign_template`). `summary.weekly_budget_by_channel`
  и `weekly_budget_total` показывают реальные суммы; превышение диапазона по сумме
  канала выводится как информационное предупреждение без согласования.

Выбранные минус-фразы применяются также к РСЯ. Регистр ExcludedSites сохраняется,
поскольку строка может быть регистрозависимым Android application ID.
Каталог целей автоматически выбирается только из кампании с пересечением счётчиков;
иначе нужны `goal_catalog_campaign_id` или существующий явный `allow_unverified_goals`.

Аудит помечает неподдерживаемые типы кампаний как `MANUAL` с причиной. Если
усечены настройки, объявления, группы, фразы или корректировки, `ready=false`,
`source_truncated=true`, а `incomplete_sources` перечисляет источники. Readback
также не подтверждает неполную выборку; созданные фразы читаются пачками по 10000 ID.

В `direct_report` доступен `include_discount` (по умолчанию false), он сохраняется
в метаданных. В `direct_client_report` тот же параметр задаётся в `configuration`.
Контекст целей/атрибуции использует сокращённый снимок настроек с кэшем до 5 минут
на логин и набор кампаний; запись кампаний/стратегий через этот клиент сбрасывает кэш.
`settings_read_at` показывает время исходного снимка. Архив сохраняется в выборке
для корректного согласования исторических отчётов. `Page.Limit` разрешён без `OrderBy`.

## direct_campaign_repair

Preview/apply ограниченных исправлений существующих ЕПК.

Поддержаны минус-фразы/приоритетные цели кампаний, отдельные поля
ResponsiveAd и настройки автотаргетинга. До preview выполняется live preflight
объектов, дополнений и конечных ссылок с наследуемыми метками (desktop/mobile).
Токен связан с логином, хешем плана и проверенным снимком. После подтверждения
состояние перечитывается; изменение требует нового preview. Показы не запускаются.

Пропущенное поле сохраняется; display_url_path:null и sitelink_set_id:null очищают
поле, ad_extension_ids:[] удаляет уточнения. Вложенные ID принимаются строками
либо целыми числами. Readback проверяет точный состав уточнений и сохранность
остальных читаемых настроек; флаг наличия дополнений не считается доказательством.

При ремонте существующего объявления можно передать `ads[].ad_image_hashes`
с полным набором из 1–5 различных непустых хэшей. Для РСЯ по политике требуется
3–5 изображений. Остальные поля объявления можно опустить: MCP прочитает
их для preflight и проверки сохранности, но не включит в update.
MCP использует формат обновления `AdImageHashes: {Items: [...]}`, перед записью
проверяет принадлежность объявлений и доступность изображений, сохраняет исходные
объявления в результате и сверяет полный набор хэшей после записи.
Отсутствие поля сохраняет текущие изображения. Карусели этим полем не задаются.

## direct_ad_assets_create

Preview/apply создания наборов быстрых ссылок, уточнений и изображений.

`assets_bundle.images`: до 100 объектов `{path, name, type}`; `path` — абсолютный
путь к PNG/JPG/GIF до 10 МБ. Вместо пути можно передать `image_data` в base64.
`type`: `AUTO` (по умолчанию), `REGULAR`, `WIDE`, `FIXED_IMAGE` (до 512 КБ).
Размеры и соотношение сторон окончательно проверяет Direct API. Preview возвращает
`image_manifest` с SHA-256, размером и именем без передачи бинарных данных в ответ.
Файл перечитывается перед подтверждённым apply; изменённые байты меняют хеш плана.
Загрузка выполняется через `AdImages.add` пачками по 3, полученные `AdImageHash`
проверяются через `AdImages.get` и передаются в `ads[].ad_image_hashes`.
При частичном ответе сохраняются уже выданные ID/хэши. Загрузка основного
изображения не выполняет отдельную ручную настройку карусели.

Первый вызов только валидирует и возвращает одноразовое подтверждение.
Созданные ID затем передаются в campaign_bundle или direct_campaign_repair.
Минимум 4 ссылки, рекомендуется 8 с описаниями. Один набор переиспользуется
всеми релевантными объявлениями, а не создаётся заново для каждого.

## Формат результата и артефакты

Все тулы возвращают structuredContent и совместимый текстовый JSON; isError отмечает ошибку. direct_campaign_plan и direct_campaign_audit по умолчанию возвращают сводку, полный JSON сохраняется в artifact_path. save_artifact=false явно включает прежний полный ответ без файла. Preview direct_campaign_apply всегда сохраняет план и preflight без одноразового токена. Полный раздел читается direct_read_artifact по JSON Pointer; json_fragment продолжается через next_offset (символы, не строки). Сводка может сокращать вложенные массивы; перед подтверждением проверяйте полный план. direct_read_report автоматически возвращает raw_lines для повреждённого TSV: offset считает физические строки с 0, включая заголовок.

Для нативного CallToolResult требуется mcp>=1.19.0,<2.0.0.


## Кнопка и изображения РСЯ — политика 1.11.0

`ads[].action_button`: объект с `text` (наиболее релевантная подпись из доступных
в UI), `reason` (обоснование), `destination` (`main` по умолчанию либо `contacts`),
`href`. Для `main` URL подставляется из `ads[].href`; для `contacts` нужен явный
проверенный URL контактов на том же сайте. Кнопка обязательна при наличии `href` и изображения или видео.
Для текстового Поиска без медиа она необязательна. Это метаданные для UI, в API `ResponsiveAd` они не отправляются.
Preflight проверяет URL кнопки с метками на desktop и mobile. После создания
агент сохраняет кнопку в интерфейсе и повторно открывает объявление для проверки
текста и URL; API-аудит оставляет `ads.action_button=MANUAL`.

В каждом объявлении РСЯ нужны **3–5 разных изображений**: подготовьте или
сгенерируйте минимум 3 самостоятельных креатива, загрузите все через
`direct_ad_assets_create(images)` и передайте `ad_image_hashes` одного объявления.
Один хэш и дубли не проходят план. `direct_ads` возвращает `ad_image_hashes` и
`image_count`, readback сверяет весь набор с планом. Генерацию выполняет агент
инструментом изображений или в интерфейсе, сам сервер изображения не генерирует.
Карусель остаётся отдельным требованием. `required_manual_actions` содержит
точный выбор кнопки и ID созданных объявлений; `setup_complete=false`, пока есть
обязательные UI-действия. Полный порядок: `direct://kb/agency-policy`.


## Изменения протокола после аудита 11.09.2026

`direct_write_job(client_login, job_id)` читает результат фонового preview/apply.
При `running` повторите чтение через `poll_after_seconds`; оно не возобновляет запись.
Write-тулы дополнительно требуют согласия через MCP elicitation. ID во всех JSON
возвращаются строками. Журнал сохраняет каждый write-запрос и ответ, неизвестный
исход удерживает блокировку логина. Полный контракт, кеш, порядок сверки, новые
поля цены/ЕРИР/IP/минус-наборов/ретаргетинга: `direct://kb/api-contract`.

`direct_list_clients(limit=1000, offset=0, include_archived=false)` возвращает
`truncated` и `next_offset`; продолжайте страницы до `truncated=false`. Поля
баланса этот инструмент не получает. При `include_archived=true` включает архивных.


## direct_verify_job и независимые статусы

`direct_verify_job(client_login, job_id, campaign_bundle?, repair_bundle?)`
доступен в campaign_setup. Выполняет только GET для завершённого apply/repair job
без uncertain; не повторяет запись, не запускает показы и не переиздаёт отчёт.
Исходный bundle нужен только старому job без сохранённого плана; логин и полный
plan_hash обязаны совпасть. Старый repair без before не может получить полную
приёмку. Результат — отдельный артефакт с verification_id, job_id, plan_hash,
source_journal_sha256 и checked_at; оригинальный журнал не меняется.

Читайте direct_write_job.current_verification для последней сверки (включая
неуспешную), верхний status описывает оригинальный результат. workflow разделяет
api_creation, api_verification, ui_verification, setup, publication и launch.
setup_complete требует полного создания и успешной проверки; ожидание явного
запуска/модерации не относится к настройке. API-хеши не доказывают сохранение
кнопок/каруселей: ui_verification остаётся pending до независимой UI-приёмки,
которую этот API-инструмент не выполняет. launch=requires_explicit_instruction
описывает разрешение, не live-состояние показов. scope=repair относится только
к согласованным исправлениям. Публикация отражает исходный результат отчёта.

Изображения до preview и до первой записи декодируются через Pillow.
Проверяются REGULAR/WIDE/FIXED_IMAGE и AUTO по размерам Директа, 10 МиБ (512 КиБ
для FIXED_IMAGE), все кадры; локальные пределы 200 кадров / 100 млн пикселей.
image_manifest включает width, height, format, matched_type, frames, decoded,
sha256. Повреждение любого файла блокирует весь запрос до создания дополнений.


## Эксплуатация: реестр, публикация и версия

`direct_pending_actions(client_login, offset=0, limit=100)` читает локальные журналы
и возвращает незавершённые действия с устойчивыми action_id, job_id, правилом и
статусом. Учитывает последнюю API-сверку и последнюю попытку публикации; UI и запуск
не закрываются по одному лишь API-успеху. Это реестр известных локальных операций,
не полный аудит кабинета. `next_offset` указывает следующую страницу; `complete=false`
означает повреждённые/нечитаемые записи. `login_locked` показывает блокировку,
не снимая её. Операции running из другого процесса помечаются owner_changed.

`direct_publish_job(client_login, job_id)` создаёт preview восстановления публикации
существующего HTML завершённого apply job. Полный хеш связывает исходный журнал,
байты HTML и SSH/root/public URL назначения. Новый snapshot отчёта сохраняется
в jobs/reports, включая случай ошибки публикации. Для старых jobs нужен сохранённый
путь к HTML; если пути нет, инструмент отклоняет запрос и не подбирает чужой файл.

Вызов с confirmation требует MCP elicitation и повторной проверки под блокировкой
логина. Создаётся отдельный publish job с source_job_id, журналом запроса/результата,
backup и публичным HTTP/SHA-256 readback. Рекламный API не вызывается. При ошибке
нужен новый preview; неизвестный исход удерживает блокировку до ручной сверки.
Чтение исходного job показывает current_publication, сохраняя исторические поля.
Не повторяйте direct_campaign_apply для восстановления отчёта.

`direct_runtime()` доступен в обоих режимах: версия пакета, protocol_revision,
process_id/PID, время старта, Python/зависимости, пути, безопасные флаги конфигурации,
хеш исходников на старте и сейчас, restart_required. Токены не возвращаются.
Одинаковая версия пакета при локальных правках различается по SHA-256 исходников.
После обновления перезапустите MCP только при отсутствии активных записей и
проверьте новый process_id, protocol_revision и restart_required=false. Preview-токены
старого процесса недействительны. Реестр и runtime не создают рекламный API-клиент.
