# Агентская политика `agency_default_v1`

## Версионируемые бизнес-профили — 18.09.2026

`agency_default_v1` зафиксирован на 1.12.0 для совместимости. Для новых планов
для услуг/B2B и локального бизнеса выбирайте _new_v1 / _established_v1.
Для товарного e-commerce используйте ecommerce_new_v2 / ecommerce_established_v2
(версия 2.0.0); e-commerce v1 сохранены для прежних планов. У каждого профиля
собственный снимок и хеш. Контракт товаров: `direct://kb/product-campaigns`.
Правила ниже описывают legacy-базу; точные отличия, цели, структура, история,
стратегии и обоснованные исключения: `direct://kb/policy-profiles`.
Новые профили сохраняют общий лимит только на кампании плана и не запускают показы.

## Измерение и проверки — политика 1.12.0, 18.09.2026

- Для нового плана используйте `tracking_profile=utm_v1`: UTM source=yandex,
  medium=cpc, campaign={campaign_id}, content={ad_id}, term={phrase_id};
  прежние BI-параметры сохранены. `regulation_v1` доступен явно для совместимости.
- Явно задайте `client_budget` (amount, period=weekly/monthly, currency,
  includes_vat; vat_percent при сумме с НДС). Лимит относится только к кампаниям
  этого плана, включая все варианты. Существующие кампании не учитываются.
  Распределение weekly_budget задаётся отдельно; сумма не может превысить лимит.
  Месячная сумма без НДС × 12/52 — средний недельный эквивалент, не календарный
  месячный потолок. Валюта сверяется с кабинетом. Старый пропуск = not_configured.
- Автотексты явно выключены: `ALTERNATIVE_TEXTS_ENABLED=NO`. Включение через
  `settings.ALTERNATIVE_TEXTS_ENABLED=true` требует осознанного выбора.
- Для каждого BusinessId нового bundle нужны ожидаемые `business_profiles`:
  business_id, phone, address (null допустим без офиса), has_office. До и после
  записи сверяются опубликованность, телефон, адрес и наличие офиса.
- `strategy.goal_id=13` выбирает PriorityGoals; нужен хотя бы один ID кроме 12.
  13 не является отдельной целью и не допускается в priority_goals. Каталог
  проверяется по реальным ID, readback — по точному GoalId стратегии.

Подробный контракт и примеры: `direct://kb/tool-reference`.

## Стартовый тест — актуальное правило от 18.09.2026

Поиск + РСЯ — стандарт для услуг/B2B и локального бизнеса; для интернет-магазина —
товарная кампания + Поиск. Ориентир — 30 000 RUB в месяц на весь создаваемый план.
По правилу пользователя суммы достаточно для стандартного теста; не сокращать
его до одного канала только по бюджету. Полнее покрывать релевантные направления
и креативные гипотезы в общем лимите. Правило действует для new и established.
Явное задание клиента приоритетно. НДС и доли кампаний фиксируются отдельно.

Это заменяет прежний ориентир по 5 000 RUB без НДС в неделю на Поиск и РСЯ;
старые планы сохраняются. Текущее правило возвращается в planning_defaults вне
снимков policy. Товарные форматы ещё не создаются компилятором; обычная РСЯ их
не заменяет. Подробности и ограничения: `direct://kb/policy-profiles`.

## Подготовка и применение после аудита 11.09.2026

Недостающие сведения, включая бюджет, выяснить в начале задачи. Затем
самостоятельно подготовить и проверить полный план и назначение отчёта.
Перед записью MCP-клиент запрашивает согласие через elicitation на конкретный
логин и полный хеш плана. `confirmation` остаётся техническим одноразовым токеном
целостности и сам по себе не разрешает запись. Решение, хеш, время и имя клиента
сохраняются в журнале. Участие человека обеспечивает доверенный интерфейс клиента;
сервер фиксирует `client_attested`, а не удостоверенную личность человека.

Запуск и возобновление показов требуют отдельной явной команды пользователя.
Preview, live preflight, независимый readback, резервные копии и проверки
публикации сохраняются. `BLOCK`, неполные выборки и дубли останавливают запись.
Разрешения среды исполнения и границы доступа это правило не изменяет.

## Кнопка и изображения РСЯ — политика 1.11.0

В каждом комбинаторном объявлении РСЯ обязательны **3–5 разных изображений**.
До планирования подберите или сгенерируйте минимум три самостоятельных креатива:
разные сюжеты, ракурсы или преимущества, релевантные конкретному предложению.
Не дублируйте один файл и не считайте три кадрирования одной фотографии тремя
самостоятельными креативами. Проверьте визуально качество и соответствие посадочной.
Генерацию выполняет агент инструментом изображений или в интерфейсе Директа;
сам MCP-сервер изображения не генерирует. Загрузите все через
`direct_ad_assets_create(images)` и передайте хэши в `ad_image_hashes` одного
объявления. План и исполнитель блокируют менее трёх уникальных хэшей; аудит
считает фактические хэши из `Ads.get`, readback сверяет весь набор с планом.
Это обычные варианты изображений; отдельная карусель РСЯ по-прежнему обязательна.

Для объявления с `href` и изображением/видео агент выбирает **наиболее релевантную кнопку**
из доступных вариантов интерфейса по предложению, намерению и целевому действию.
Для покупки выбирайте вариант покупки, для записи — записи, для обращения —
заявки или связи, если соответствующий вариант есть в интерфейсе и действие
доступно на посадочной. Нейтральный вариант допустим, когда точнее подходящего нет;
не выбирайте его одинаково для всех объявлений без оценки предложения.

В `ads[].action_button` передайте `text` (точная подпись из интерфейса), `reason`
(почему она подходит), `destination` (`main` по умолчанию либо `contacts`) и `href`.
Для `main` ссылка автоматически подставляется из `ads[].href`; для `contacts`
обязательна явная проверенная страница контактов на том же сайте. Не угадывайте
путь `/contacts`. Preflight проверяет URL кнопки с эффективными метками на desktop
и mobile. Для объявления с медиа без выбора текста и обоснования план блокируется.
Текстовый Поиск без медиа не требует кнопки.

```json
"action_button": {
  "text": "Узнать больше",
  "reason": "На посадочной описаны условия услуги, более точного действия нет",
  "destination": "main"
}
```

`action_button` — метаданные задания, а не поле `ResponsiveAd` публичного API.
Точные текст и URL сохраняются в плане и привязаны к его хешу. После создания
агент обязан заполнить их через интерфейс, сохранить и повторно открыть каждое
объявление, проверить выбранную подпись, полный URL и страницу перехода.
`required_manual_actions` содержит задания `ads.action_button` и `network.carousel`
с точными ID созданных объявлений. API-аудит оставляет кнопку `MANUAL`, пока её
не проверили через интерфейс; `setup_complete=false` отделяет создание объектов
от завершения настройки. Недоступность браузера не означает выполненную настройку.

Источники: [Кнопка действия](https://yandex.ru/support/direct/ru/efficiency/button),
[Ads.add](https://yandex.ru/dev/direct/doc/ru/ads/add),
[Ads.get](https://yandex.ru/dev/direct/doc/ru/ads/get), проверены 10.09.2026.

## Возрастные ограничения и интересы аудитории — политика 1.9.0

`age_min` принимает 0, 18, 25, 35, 45, 55; `age_max` — 17, 24, 34, 44, 54 или
null (без верхнего ограничения). Границы должны совпадать с возрастными группами
API. Например, `age_min:25, age_max:54` создаёт −100% для AGE_0_17, AGE_18_24,
AGE_55. Независимый readback сверяет все исключения. Ответ BidModifiers.add
содержит массив `Ids`; исполнитель сохраняет и учитывает каждую корректировку.

Интересы необязательны и выбираются для конкретной кампании. MCP не задаёт
отраслевые аудитории по умолчанию: названия и ID интересов хранятся в клиентском
плане. Если `audience_interest_ids` отсутствует, условия по интересам не создаются.

В группе РСЯ можно указать `audience_interest_ids` (1–10 уникальных ID из
Dictionaries.AudienceInterests, только SHORT_TERM) и `audience_priority`
(LOW/NORMAL/HIGH, по умолчанию NORMAL). Такие группы отдельные: без ключей,
автотаргетинга и offer_retargeting. Долгосрочные и ANY интересы в этом варианте
ЕПК не поддерживаются. До подтверждения preflight проверяет ID и длительность
по живому каталогу и показывает названия интересов.

Исполнитель создаёт RetargetingList типа AUDIENCE с одним правилом ANY,
затем привязывает AudienceTarget к созданной группе. Он не использует InterestId
для мобильных приложений. ID обоих объектов сохраняются при частичной ошибке;
повторять весь пакет нельзя. Readback проверяет группу, ID, интересы, приоритет,
доступность и отсутствие параллельных ключей. Усечённые ответы не считаются успехом.

Источники, проверено 09.09.2026:
[Возрастные корректировки](https://yandex.ru/dev/direct/doc/ru/bidmodifiers/add),
[RetargetingLists.add](https://yandex.ru/dev/direct/doc/ru/retargetinglists/add),
[AudienceTargets.add](https://yandex.ru/dev/direct/doc/ru/audiencetargets/add),
[Интересы в ЕПК](https://yandex.ru/support/direct/ru/products-text-image-ads/user-profile).


Это машиночитаемая версия регламента настройки кампаний. Её полный JSON отдаёт
`direct_policy`; `direct_campaign_audit` применяет те же правила к фактическим
настройкам из API v501. Версия политики фиксируется в каждом артефакте аудита,
поэтому результат можно воспроизвести после изменения регламента.

## Максимум кликов без Метрики — версия 1.8.2

Для `maximum_clicks` счётчик и бизнес-цели необязательны: `counter_ids` и
`priority_goals` можно опустить или передать пустыми массивами. Компилятор
не отправляет пустые `CounterIds`/`PriorityGoals` и не подставляет фиктивную
цель. Если цели не выбраны, `goals_reviewed`, каталог целей и
`allow_unverified_goals` не требуются. Счётчик без выбранных целей допустим.
Если бизнес-цели указаны, сохраняются проверка счётчика, ручное подтверждение
целей и live-проверка каталога. Для `maximum_conversion_rate` по-прежнему
обязательны счётчик и явный `goal_id` из `priority_goals` либо селектор 13
при наличии хотя бы одной приоритетной цели кроме системной 12.

Основание: [UnifiedCampaign.add](https://yandex.ru/dev/direct/doc/ru/campaigns/add-unified-campaign):
`CounterIds` необязателен, `WB_MAXIMUM_CLICKS` не требует `GoalId` или
`PriorityGoals`. Проверено 09.09.2026.

## Статусы

С версии 1.8.1 обязательна проверка конечных ссылок с метками и подставленными
динамическими значениями (основные + быстрые, компьютер + телефон). Проверка
только Href без меток недостаточна. Непроверенные ссылки, сетевые ошибки и
soft-404 блокируют положительный итог. Параметр названия кампании в regulation_v1:
`yd_campaign_name={campaign_name}`, не `name={campaign_name}` (конфликт WordPress).

Дополнение по компилятору: выбранные с учётом бизнеса минус-фразы передаются
во все создаваемые каналы, включая РСЯ. Для нескольких кампаний одного канала
бюджет задаётся явно у каждого варианта, а сумма проверяется и отображается
отдельно. Часовой пояс указан в плане явно; возрастное ограничение аудитории
`age_min` и маркировка объявления `age_label` — независимые параметры.

API допускает 1–3 текста, но агентская политика по-прежнему требует ровно 3.
Бюджет на произвольный период, стратегии CRR и другие виды корректировок ставок
не поддерживаются typed-компилятором. Поле `IsMetrikaSourceOfValue=YES`
разрешено API только для CRR, поэтому для двух доступных стратегий оно отклоняется.
Эти ограничения не обходятся передачей произвольного API-объекта.

- `PASS` — требование подтверждено данными API.
- `WARNING` — настройка возможна, но это осознанное отклонение, которое должен
  принять специалист.
- `BLOCK` — обязательное правило нарушено; будущий исполнитель не должен
  применять такой план.
- `MANUAL` — Direct API не даёт достаточных данных. Такой пункт нельзя молча
  считать выполненным.

## Структура и семантика — версия 1.6.0

Новые типизированные планы требуют реестр `semantic_plan` и обоснование `semantic`
каждой группы. Одна группа объединяет связное намерение, предложение и основную
посадочную. Источники, даты, география, решения по кандидатам и история фиксируются
до создания; сформированные моделью фразы отмечаются гипотезами.
Ориентиры малого проекта: Поиск 3–10 групп × 10–30 ключей, РСЯ 2–5 × 5–15.
Допустимы объяснимые отклонения; каталогу нужен отдельный профиль с обоснованием.
Число объявлений 1–3 сохраняется; для нескольких обязательны разные гипотезы.
Технические пределы проверяются в компиляторе и executor; существующие кампании
не перестраиваются. Полный контракт: `direct://kb/structure-semantics`.

## Сохраняющиеся правила версии 1.5.0

Поиск, РСЯ и условные Карты разделяются на отдельные кампании. Недельный бюджет
каждой кампании рекомендуется от 2 000 до 5 000 в валюте кабинета. Это значение
по умолчанию, а не универсальный потолок: выход за диапазон даёт подтверждаемое
`WARNING`. Базовые стратегии — максимум кликов или максимум конверсий с
ограничением недельным бюджетом; средняя CPA и оплата за конверсии блокируются.
`TrackingParams` задаются на уровне кампании и сверяются с именами и шаблонными
значениями профиля `utm_v1` (или явно выбранного `regulation_v1`).
Для Поиска минус-фразы выбираются по бизнесу, для РСЯ —
исключённые площадки. Для географии проверяются регионы на уровне групп.

Снимки из 249 минус-фраз и 248 площадок сохранены с SHA-256. Список площадок
применяется как раньше. Минус-список доступен только при явном выборе
`negative_keyword_policy.profile=legacy_reviewed`; ни одно его слово не является
универсально обязательным. По умолчанию профиль `custom` пустой.

Профили `rental`, `education`, `toys` — небольшие агентские гипотезы для аренды,
обучения и игрушек, а не требования Яндекса. Обязательной минусовки «прокат»,
«урок», «игрушка», «перевод» или вариантов «бесплатный» нет. Укажите товары и
услуги в `business_terms`; пересекающиеся с ними кандидаты профиля исключаются
с объяснением. `additions` и `exclusions` имеют поля `phrase` и `reason`.
Исключения сопоставляются по нормализованной записи с сохранением операторов:
для иной словоформы или варианта с `!` задайте отдельное исключение.
Исходные поля `additional_negative_keywords` и `approved_risky_negatives`
сохранены как явные дополнения. Их причина в плане — «явно передано».

Preview содержит `negative_keyword_selection` со всеми выбранными и исключёнными
фразами и причинами. Пересечения с товаром, текстами и ключами дают `WARNING`
`search.negative_context_conflict`, требующий осознанного подтверждения. Это
кандидаты на проверку: локальная эвристика не воспроизводит морфологию и аукцион
Директа. Аудит учитывает также уже прочитанные title/H1/description посадочной;
сайт при локальной компиляции не загружается. Семантическая проверка запроса,
ассортимента и общей минусовки остаётся `MANUAL`. Отсутствие общего списка не
даёт `BLOCK`, и неизвестный бизнес не означает доказанную безопасность минусов.

Дополнительный контекст в `negative_keyword_policy`: `search_queries` — массив
строк из отчёта по поисковым запросам, `landing_texts` — выдержки посадочной.
Компилятор проверяет пересечения и сохраняет источник `provided_in_bundle`;
самостоятельную загрузку этих данных он не заявляет. Групповые минус-фразы
отражаются в `group_selections`; для старого строкового формата фиксируется факт
явного задания и необходимость уточнить бизнес-причину при проверке.

Новая группа содержит 1–3 `ResponsiveAd`; стартовая рекомендация — одно полное
объявление, дополнительные нужны для отдельных гипотез. Технический предел
Яндекса — 3 неархивных и 10 с архивными. Перенесённая Яндексом существующая
группа с большим числом требует проверки миграции, а не автоматического удаления.
Источник: [создание комбинаторного объявления](https://yandex.ru/support/direct/ru/unified-performance-campaign/create-comb-ad).

Конверсионные отчёты используют выбранные цели и модель кампании; неоднородные
настройки требуют отдельных отчётов либо явных `goals` + `attribution_models`.
Подробности и метаданные — `direct://kb/report-recipes`. Проверено 5 сентября 2026.

## Геотаргетинг

Регионы задаются на уровне групп. MCP проверяет ID регионов и подтверждение
`regions_verified`. Алгоритмы геотаргетинга применяются автоматически; отдельного
переключателя нет. Система учитывает намерение купить в выбранном регионе,
поэтому регион не означает жёсткую фильтрацию по текущему местоположению.
Источник: [обновление Яндекса](https://b2b.yandex.ru/adv/news/obnovlenie-geotargetinga-v-direkte).

## Быстрые ссылки — версия 1.2.0

Минимум 4, предпочтительно 8 полезных ссылок с описаниями. Это агентский минимум:
API технически разрешает 1–8. Одинаковое содержание оформляется одним набором,
а его ID переиспользуется. В bundle общий `sitelink_set_id` наследуется в порядке:
объявление → группа → канал/вариант кампании → bundle; `campaign_template`
передаёт значение вариантам. На стороне API компилятор записывает ID в объявления.
Настройки быстрых ссылок кампании и группы в веб-интерфейсе — отдельный механизм,
публичные методы API создания кампаний/групп этих полей не предоставляют.

Preflight читает уникальные наборы одним пакетным запросом (до лимита API).
Менее 4 или более 8 блокирует запись; 4–7 допустимо, но рекомендуется 8.
Аудит проверяет содержимое набора, а не только наличие ID. Неизвестное количество
или потенциальное наследование из интерфейса даёт `MANUAL`, не `PASS`.
Не добавлять нерелевантные страницы или дубликаты ради числа 8.

Источники: [настройка в интерфейсе](https://yandex.ru/support/direct/efficiency/quick-links.html),
[наборы API](https://yandex.ru/dev/direct/doc/ru/sitelinks/add),
[поля объявления](https://yandex.ru/dev/direct/doc/ru/ads/update).

## Что остаётся ручным

Direct API не сообщает цвет и новизну целей в интерфейсе, а наличие физического
офиса нельзя достоверно вывести из кампании. Поэтому вместо автоматического
выбора «всех зелёных» специалист подтверждает небольшой набор бизнес-целей и их
ценность; исключение поиска по сайту и просмотров страниц и необходимость
отдельной кампании в Картах остаются `MANUAL`.

Источник политики: регламент Google Docs и две связанные таблицы, URL и дата
последней наблюдавшейся модификации сохранены внутри `direct_policy`.

## Карусель РСЯ — версия 1.4.0

В каждом объявлении РСЯ **всегда добавлять отдельное дополнение «Карусель»**
(галерею) из 2–10 релевантных изображений. Использовать фотографии клиента с
его сайта или согласованные материалы; сохранять исходные URL и порядок слайдов.
Обычные варианты `ResponsiveAd.AdImageHashes` не являются каруселью.
Основное изображение объявления обязательно. Каждый слайд: JPG, PNG или GIF
(только первый кадр), обе стороны не менее 450 px, файл не более 10 МБ.
Разница отношения сторон дополнительного слайда и первого слайда — строго меньше
0,15. Изображения должны соответствовать предложению и посадочной странице.

Публичные схемы Direct API не предоставляют поля карусели. Поэтому компилятор
создаёт `required_manual_actions` для каждого объявления РСЯ; исполнитель
подставляет ID созданных объявлений строками, сохраняя точность больших чисел.
После записи через API открыть объявления в интерфейсе, добавить карусель
(можно массовым редактированием), сохранить и повторно открыть каждое объявление.
Зафиксировать ID объявления, время проверки, число и порядок слайдов и снимок
или наблюдение сохранённого интерфейса. Только после этого действие выполнено.
Аудит API оставляет `network.carousel=MANUAL` даже при нескольких AdImageHashes;
доказательство проверки интерфейса хранится отдельно, не подменяя API-аудит.

`status=complete` / `api_creation_complete=true` означает завершение записи
объектов через API. Невыполненные `required_manual_actions` не позволяют объявить
настройку завершённой. Недоступность браузера — незавершённый этап: сохранить
список ID и слайды, сообщить пользователю и продолжить после восстановления.
Если формат не поддерживает дополнение, зафиксировать конкретную причину;
не пропускать правило молча. Готовый клиентский отчёт обновляется только по
фактически сохранённым настройкам. Наличие карусели не гарантирует показ на каждой
площадке: формат выбирает Директ, изображения проходят модерацию.

Источники: [Карусель](https://yandex.ru/support/direct/ru/efficiency/carousel),
[Ads.add](https://yandex.ru/dev/direct/doc/ru/ads/add),
[Ads.update](https://yandex.ru/dev/direct/doc/ru/ads/update).
