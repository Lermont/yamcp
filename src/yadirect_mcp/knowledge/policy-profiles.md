# Профили бизнеса и готовности данных

## Текущие стартовые правила — 25.09.2026

Новые планы: бизнес-профили `*_new_v4` / `*_established_v4` для services_b2b,
local_business и ecommerce. Стратегия — максимум конверсий с оплатой за клики
(`WB_MAXIMUM_CONVERSION_RATE`), без целевой CPA и без требования истории.
Одна проверенная цель — её ID; несколько — GoalId=13. Максимум кликов выбирается
при отсутствии Метрики или целей. Ошибка проверки не равна отсутствию.

Бюджет v3/v4 по умолчанию: **30 000 RUB с НДС на 14 дней**, на все кампании плана.
Незаданные поля client_budget: amount=30000, period=two_weeks, currency=RUB,
includes_vat=true, vat_percent=22 (РФ, 2026). Явные значения имеют приоритет;
для другой валюты ставку задавать явно. Доли кампаний назначать без НДС:
общий недельный лимит = amount / (1 + vat_percent/100) / 2 с округлением вниз
до микроединицы. Для стандартного бюджета это 12 295,081967 RUB в неделю.
Это расчёт распределения, не автоматическое завершение показов через 14 дней.
Стандартный состав: Поиск + РСЯ; для магазина — товарная кампания + Поиск.

`YD_APPROVAL_MODE=task_authorized` выполняет конкретное поручение пользователя
без повторных форм. Клиент обязан соблюдать границы задачи; режим не даёт
постоянного разрешения на публикацию или произвольные изменения аккаунтов.
Preview, SHA-256, одноразовый confirmation, preflight, журнал и readback сохранены.
Журнал отличает configured_task_authorization / task_scope_delegated от ответа
человека на форму. По умолчанию для других установок остаётся elicitation;
отказ в этом режиме не разрешает автоматический переход к записи.

Кампании и отчёты вести в `D:\yadirect-reports`, всегда через MCP Директа;
`D:\mcp_direct` — разработка самого MCP. Context7 для этого workflow не обязателен.
После переподключения direct_runtime показывает approval_mode и протокол
2026-09-25-network-neuro-schedule-v4. Профили v1/v2/v3/legacy сохранены:
новые планы используют v4. В v4 автотексты включены по умолчанию через API;
нейрообъявление требуется через интерфейс отдельно, одно на группу по
`semantic.landing_url`. Сохранить и проверить генерацию; это
`required_manual_actions.ads.neuro_ad`, не подтверждение создания через API.
Явные `settings.ALTERNATIVE_TEXTS_ENABLED=false` и `groups[].neuro_ad=false`
сохраняются. Полный график, включая праздники 00:00–24:00 при 100%, использует
штатное 24/7 без сетки часов. Repair: `campaigns[].schedule=always_on` сбрасывает
старый график; `campaigns[].alternative_texts_enabled=true` включает автотексты.
`new_groups[].channel=network` добавляет группы в остановленную ЕПК РСЯ.

Источники: [НДС Яндекса](https://yandex.com/support/direct/ru/statistics/new-reports-wizard/settings/tax),
[контракт ЕПК](https://yandex.ru/dev/direct/doc/ru/campaigns/add-unified-campaign).

С 18.09.2026 новые планы могут явно выбирать `policy_name`. Доступные имена
возвращает `direct_policy.available_profiles`; сам инструмент ничего не меняет
в кабинете. Профили версии 1.0.0 основаны на зафиксированной политике 1.12.0.

| Бизнес | Без истории | Со статистикой | Основные отличия |
|---|---|---|---|
| Услуги / B2B | `services_b2b_new_v1` | `services_b2b_established_v1` | Цели: qualified_lead, lead, order. Точная семантика; Карты по необходимости |
| Локальный бизнес | `local_business_new_v1` | `local_business_established_v1` | Цели: phone_call, appointment, order. Офис, Карты и контакты обязательны; более компактные группы |
| E-commerce, прежние планы | `ecommerce_new_v1` | `ecommerce_established_v1` | Версия 1.0.0 сохранена без изменений |
| E-commerce, товарные форматы | `ecommerce_new_v2` | `ecommerce_established_v2` | Версия 2.0.0; purchase, catalogue, product с ShoppingAd/ListingAd |

`new` означает отсутствие истории для выбора стратегии, а не возраст договора
с клиентом. `established` требует источник статистики. Достаточность данных
оценивается отдельно для каждой кампании по каналу, набору регионов и цели.
Название профиля само по себе не разрешает конверсионную стратегию.

## Стартовый тест — правило пользователя от 18.09.2026

- Для услуг/B2B и локального бизнеса стандарт — **Поиск + РСЯ** отдельными кампаниями.
- Для интернет-магазинов стандарт — **товарная кампания + Поиск**.
- Если иной бюджет не указан, ориентир — **30 000 RUB с НДС на 14 дней суммарно** на
  кампании создаваемого плана. По правилу пользователя этой суммы достаточно
  для стандартного теста: сама сумма не служит причиной оставлять один канал.
  Это рабочее правило агентства, а не гарантия результата рекламы.
- Правило одинаково для new и established. История влияет на анализ
  и распределение бюджета, но сама по себе не отменяет стандартный состав теста.
- Предпочитать полное покрытие релевантных направлений, семантики и креативных
  гипотез в пределах общего бюджета. Не сокращать настройку автоматически;
  исключения объяснять конкретными данными или явным заданием клиента.
  Количество групп определяется предложением и посадочными, без дублей ради числа.
- Явные условия клиента имеют приоритет. Доли кампаний задавать отдельно;
  включает ли сумма НДС и ставку при includes_vat=true фиксировать явно.
  Карты локального профиля также входят в общий лимит. Бюджет существующих
  кампаний не учитывается, автоматического увеличения расхода нет.

Текущие рекомендации доступны как `direct_policy.planning_defaults`, отдельно
от зафиксированных `policy` и их хешей. `campaign_mix` описывает сценарий
планирования. `bundle.channels.product` поддержан в e-commerce v2: товарная
галерея и сети с общим бюджетом, ShoppingAd/ListingAd, источник, фильтры и
проверка обработки. `search` задаётся отдельно. Источник — URL-фид из задания
либо созданный в интерфейсе фид по сайту с товарной разметкой, доступный API.
Полный контракт: `direct://kb/product-campaigns`.
Явно согласованный иной состав технически допустим; компилятор сам кампании не добавляет.

Правило заменяет прежний ориентир по 5 000 RUB без НДС в неделю для Поиска и РСЯ.
Нельзя применять его поверх 30 000 с НДС на 14 дней: недельные доли рассчитываются от
общего лимита на 14 дней после учёта НДС. Старые планы и их версии сохранены.

## Совместимость

Без `policy_name`, как и при явном `agency_default_v1`, действует прежняя политика
1.12.0. Её JSON сохранён с проверкой SHA-256. Прежние bundle не получают новые
поля и автоматически не мигрируют; контрольные планы и их хеши совпадают.
Правило обязательных Карт при office=true, прежний список исключений площадок
и диапазон 2 000–5 000 сохраняются именно в legacy-профиле.

Бизнес-план хранит имя/версию, полный `policy_snapshot`, `policy_fingerprint`,
`profile_context`, `profile_office` и `profile_decisions`. Всё входит в plan_hash.
Смена профиля или источника истории требует нового preview и токена. Executor
проверяет снимок по реестру, а readback использует политику исходного плана.
Новые версии добавляются под новым именем: правила опубликованного `_v1`
не следует редактировать без сохранения прежней версии.

## Общие правила бизнес-профилей

- `client_budget` ограничивает только кампании плана; в v3 незаданные поля заполняются по правилам выше.
  Бюджеты каналов задаются явно; фиксированный ориентир 2 000–5 000 не применяется.
  Валюта и минимумы API по-прежнему проверяются. Стандартный состав теста и
  ориентир 30 000 RUB с НДС на 14 дней заданы текущими planning_defaults выше.
- `utm_v1` обязателен; BI-параметры сохраняются. Legacy-разметка доступна в
  `agency_default_v1`.
- Общий blacklist площадок не подставляется. `additional_excluded_sites` —
  явный список клиента; непустой список требует `profile_context.exclusions_reason`.
  Причина должна указывать фактический отчёт или конкретную нерелевантность.
- Автотексты остаются выключенными. Для включения нужен `autotexts_reason`.
  Ограничение расписания требует `schedule_reason`; часы бизнеса не подставляются
  автоматически. Интересы, расширение автотаргетинга и корректировки не угадываются.
- Все выбранные PriorityGoals классифицируются в `profile_context.goals`.
  В бизнес-профилях системная 12 и селектор 13 не являются элементами этого массива.
  `GoalId=13` стратегии допустим для нескольких реальных, проверенных целей.
- Сохраняются отдельные кампании каналов, требования к креативам, изображениям,
  кнопкам/каруселям, UTM, контактам, preflight, elicitation и независимому readback.
  Профиль не запускает рекламу и не меняет уже работающие кампании.

Профили v1 сохранены. E-commerce v2 добавляют товарную галерею и сети в одной
товарной ЕПК с общим бюджетом; отдельный Поиск имеет собственную долю. История
product проверяется отдельно от search/network. CRR/MaxProfit и пакетные
стратегии не добавлены. Готовность API-объектов не заменяет проверку карточек
товаров, цен, изображений, ссылок и результата фильтра в интерфейсе.

## Пример прежнего v1: новый клиент (только совместимость)

Фрагмент bundle услуг/B2B с выбранной целью; в этом примере 30 000 указаны без НДС:

```json
{
  "policy_name": "services_b2b_new_v1",
  "client_budget": {
    "amount": 30000, "period": "monthly", "currency": "RUB", "includes_vat": false
  },
  "profile_context": {
    "measurement_verified": false,
    "goals": [{"goal_id": "123456", "kind": "qualified_lead"}]
  }
}
```

Обычные поля bundle — semantic_plan, объявления, бюджеты каналов, counter_ids,
priority_goals и т.д. — также нужны. Если целей ещё нет, допустимы пустые goals,
counter_ids, priority_goals и `measurement_verified=false`: выбирается максимум
кликов. В `new` история не передаётся, конверсионная стратегия не выбирается.
Это консервативное правило профиля, а не утверждение о запрете Яндекса.

Для local_business нужны `office=true`, канал maps и BusinessId всех объявлений
Карт, с ожидаемыми business_profiles. Клик по телефону (`phone_click`) не заменяет
фактический звонок (`phone_call`). Для услуг и e-commerce наличие офиса не обязывает
создавать Карты; при выборе Карт контакты всё равно обязательны.

Для e-commerce нужны `catalog_reviewed=true` и kind=purchase у выбранных целей.
`revenue_verified` фиксирует отдельную проверку выручки; false не запрещает максимум
конверсий по покупкам и не разрешает делать выводы о достоверной выручке/ROAS.
Отсутствующий semantic_plan.profile получает catalogue; явный другой профиль
структуры сохраняется и проверяется по его правилам.

## Пример прежнего v1: клиент со статистикой (только совместимость)

Добавьте один или несколько срезов в `profile_context.history`. Пример:

```json
{
  "policy_name": "services_b2b_established_v1",
  "allow_unverified_goals": false,
  "profile_context": {
    "measurement_verified": true,
    "goals": [{"goal_id": "123456", "kind": "qualified_lead"}],
    "history": [{
      "client_login": "client-login",
      "channel": "search",
      "region_ids": [213],
      "goal_id": "123456",
      "counter_id": "987654",
      "date_from": "2026-09-01",
      "date_to": "2026-09-14",
      "conversions": 20,
      "source": "report://reviewed-search-conversions",
      "complete": true,
      "reviewed": true,
      "reason": "Проверены период, атрибуция, качество обращений и применимость бюджета"
    }]
  }
}
```

Значения условные: источник, цель, счётчик, логин и география должны относиться
к реальному клиенту и плану. Ссылку нельзя выдавать за прочитанный отчёт.
MCP проверяет форму и согласованность декларации; он **не загружает источник
из `source` и не удостоверяет цифры независимо**. `measurement_verified` и reviewed
означают результат проверки специалистом, а не доказательство проверки самим MCP.
Live preflight отдельно проверяет доступность реальных целей через каталог Direct.

В сохранённых v1/v2 автоматический выбор максимума конверсий возможен, когда:

1. measurement_verified=true и есть ровно одна выбранная бизнес-цель;
2. у среза совпадают логин, канал, полный набор регионов, цель и счётчик;
3. complete=true, reviewed=true, есть источник и обоснование;
4. период не короче 7 дней, дата окончания не старше 30 дней, будущих дат нет;
5. среднее число конверсий за неделю не меньше 10.

Иначе по умолчанию сохраняется максимум кликов с причиной в profile_decisions.
История Поиска не включает автоматически конверсии РСЯ/Карт или другого региона.
Несколько срезов одной цели/канала/географии отклоняются: сначала подготовьте
один проверенный итоговый срез. Конверсии разных целей не суммируются автоматически.

Явно заданный максимум кликов сохраняется. Явный максимум конверсий тоже требует
достаточной истории выбранной цели; для GoalId=13 — каждой из PriorityGoals.
Нельзя обойти это allow_unverified_goals=true. Для нескольких целей автоматического
выбора нет: необходимо явно указать стратегию и её GoalId.

Порог 10/неделю — консервативный критерий агентского профиля, согласованный с
рекомендациями обучения; 7 дней и 30 дней — выбранные границы проверки данных.
Они не гарантируют качество модели, достаточность нового бюджета или результат
конкретной кампании. Перед выбором проверяются экономика, атрибуция и качество
бизнес-действий; это описывается в reason.

Источники, проверены 18.09.2026:
[Максимум конверсий](https://yandex.ru/support/direct/ru/strategies/average-cpa),
[Контракт UnifiedCampaign](https://yandex.ru/dev/direct/doc/ru/campaigns/add-unified-campaign).

Отдельный `direct_campaign_audit(policy_name=...)` не имеет исходного общего
лимита и истории; такие проверки обозначаются MANUAL. Полный план и readback
сохраняют бюджетные ограничения и точные настройки.
