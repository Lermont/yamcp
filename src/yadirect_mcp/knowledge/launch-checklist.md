# Чек-лист первичной настройки

Для выполненных UI-задач кнопки, карусели и нейрообъявления фиксировать
`direct_manual_review` после сохранения и повторного открытия. Нужны точные поля,
проверяющий, время и свидетельство; сначала свежая успешная `direct_verify_job`.
Отметка в переписке или ручная замена `status` в исходном job не закрывает задачу.
Сверять `manual_review.actions`, `workflow` и `direct_pending_actions`; при изменениях
в UI вне MCP отзывать свидетельство. Срок записи — 24 часа, метод — проверка
специалистом, отдельно от API. Завершённая настройка не разрешает запуск.
Полная схема: [tool-reference](tool-reference.md#direct_manual_review).

## Текущие стартовые правила — 25.09.2026

Новые планы: бизнес-профили `*_new_v4` / `*_established_v4` для services_b2b,
local_business и ecommerce. Стратегия — максимум конверсий с оплатой за клики
(`WB_MAXIMUM_CONVERSION_RATE`), без целевой CPA и без требования истории.
Одна проверенная цель — её ID; несколько — GoalId=13. Максимум кликов выбирается
при отсутствии Метрики или целей. Ошибка проверки не равна отсутствию.

Бюджет v3/v4 по умолчанию: **30 000 RUB с НДС на 14 дней**, на все кампании плана.
Незаданные поля client_budget: amount=30000, period=two_weeks, currency=RUB,
includes_vat=true, vat_percent=22 (РФ, 2026). Явные значения имеют приоритет;
для другой валюты ставку задавать явно. Доли кампаний назначать без НДС:
общий недельный лимит = amount / (1 + vat_percent/100) / 2 с округлением вниз
до микроединицы. Для стандартного бюджета это 12 295,081967 RUB в неделю.
Это расчёт распределения, не автоматическое завершение показов через 14 дней.
Стандартный состав: Поиск + РСЯ; для магазина — товарная кампания + Поиск.

`YD_APPROVAL_MODE=task_authorized` выполняет конкретное поручение пользователя
без повторных форм. Клиент обязан соблюдать границы задачи; режим не даёт
постоянного разрешения на публикацию или произвольные изменения аккаунтов.
Preview, SHA-256, одноразовый confirmation, preflight, журнал и readback сохранены.
Журнал отличает configured_task_authorization / task_scope_delegated от ответа
человека на форму. По умолчанию для других установок остаётся elicitation;
отказ в этом режиме не разрешает автоматический переход к записи.

Кампании и отчёты вести в `D:\yadirect-reports`, всегда через MCP Директа;
`D:\mcp_direct` — разработка самого MCP. Context7 для этого workflow не обязателен.
После переподключения direct_runtime показывает approval_mode и протокол
2026-09-25-network-neuro-schedule-v4. Профили v1/v2/v3/legacy сохранены:
новые планы используют v4. В v4 автотексты включены по умолчанию через API;
нейрообъявление требуется через интерфейс отдельно, одно на группу по
`semantic.landing_url`. Сохранить и проверить генерацию; это
`required_manual_actions.ads.neuro_ad`, не подтверждение создания через API.
Явные `settings.ALTERNATIVE_TEXTS_ENABLED=false` и `groups[].neuro_ad=false`
сохраняются. Полный график, включая праздники 00:00–24:00 при 100%, использует
штатное 24/7 без сетки часов. Repair: `campaigns[].schedule=always_on` сбрасывает
старый график; `campaigns[].alternative_texts_enabled=true` включает автотексты.
`new_groups[].channel=network` добавляет группы в остановленную ЕПК РСЯ.

Источники: [НДС Яндекса](https://yandex.com/support/direct/ru/statistics/new-reports-wizard/settings/tax),
[контракт ЕПК](https://yandex.ru/dev/direct/doc/ru/campaigns/add-unified-campaign).

## Содержание посадочных — обязательное правило 18.09.2026

Проверять все обнаруженные разделы сайта по навигации, sitemap и рекламным
ссылкам. HTTP 200 недостаточно: проверить реконструкцию/разработку, полноту
предложения, соответствие направлению и путь обращения в браузере на компьютере
и телефоне. Зафиксировать непроверенные URL. Заглушки не использовать для запуска;
раздел восстановить либо оставить связанные группы выключенными. Недостатки
и условия запуска внести в отчёт. Полный порядок: `direct://kb/landing-content`.
Текущий workflow возвращается в `direct_policy.landing_review` отдельно от
зафиксированных снимков политики.

## Сначала выбрать профиль — 18.09.2026

Для нового плана явно выбрать policy_name из direct_policy.available_profiles:
услуги/B2B, локальный бизнес или e-commerce; new без истории либо established
со статистикой. Собрать profile_context с реальными типами целей, проверкой
измерения и источниками истории. Не переносить статистику между каналами,
регионами, целями или логинами. Проверить экономику бюджета и качество событий.
Не менять профиль старого плана автоматически; смена требует нового preview.
Подробные поля и критерии: `direct://kb/policy-profiles`.

## Дополнительные проверки плана — 18.09.2026

- Явно задать client_budget только на создаваемые кампании, валюту, период и
  признак НДС; ставку для суммы с НДС. Сверить сумму всех weekly_budget с лимитом.
  При месячном бюджете × 12/52 — средний недельный эквивалент, не календарный потолок.
- Проверить профиль utm_v1 и эффективные ссылки с UTM; BI-параметры сохраняются.
- В v4 передать ALTERNATIVE_TEXTS_ENABLED=YES (явный false сохраняется).
- Выполнить ads.neuro_ad через UI: одно нейрообъявление на группу по её посадочной,
  сохранить, повторно открыть и проверить результат генерации до запуска.
- Для 24/7 выбирать «Круглосуточно»; не создавать почасовую сетку со всеми часами.
- Для каждого BusinessId указать ожидаемые phone, address, has_office в
  business_profiles из согласованных контактов клиента. Сверить с Businesses.get
  до записи и независимо после неё, включая IsPublished.
- При GoalId=13 сверить реальные PriorityGoals и минимум одну цель кроме 12.
  13 — селектор, не самостоятельная цель/лид. Проверить точный GoalId после записи.

Контракт: `direct://kb/tool-reference`. Старые планы без новых полей не подтверждают
прохождение новых проверок; для их применения подготовить новый preview.

## Подготовка и применение после аудита 11.09.2026

Недостающие существенные сведения выяснить в начале; бюджет по умолчанию не переспрашивать. Затем
самостоятельно подготовить и проверить полный план и назначение отчёта.
Согласование определяется YD_APPROVAL_MODE: task_authorized исполняет поручение
без повторных форм, elicitation запрашивает согласие на логин и хеш плана.
Confirmation — одноразовый технический токен целостности. Журнал сохраняет
режим, логин, хеш и время; ответ формы и делегированное поручение различаются.
Сервер не проверяет переписку: границы задачи соблюдает доверенный MCP-клиент.

Запуск и возобновление показов требуют отдельной явной команды пользователя.
Preview, live preflight, независимый readback, резервные копии и проверки
публикации сохраняются. `BLOCK`, неполные выборки и дубли останавливают запись.
Разрешения среды исполнения и границы доступа это правило не изменяет.

## Браузер: Playwright

По прямому указанию пользователя от 11.09.2026 все действия с браузером выполнять
через Playwright с установленным Chrome, включая карусели РСЯ, кнопки,
загрузку фотографий и визуальную проверку клиентских отчётов. Использовать
отдельный авторизованный профиль; не трогать чужие профили и процессы.
CUA и браузерный плагин не использовать вместо Playwright без новой явной просьбы
пользователя. После сохранения заново открыть объект, сверить ID, содержимое,
ссылки, количество и порядок слайдов, загрузку изображений и отсутствие ошибок.
API остаётся доступен для поддерживаемых операций; это правило выбирает способ
управления браузером; отдельная команда по-прежнему нужна для запуска рекламы.

## Стандартный стартовый тест — 18.09.2026

Поиск + РСЯ, а для интернет-магазина — товарная кампания + Поиск. Ориентир
30 000 RUB с НДС на 14 дней на все кампании нового плана достаточен для стандартного
теста по правилу пользователя; не оставлять один канал только из-за суммы.
Подготовить полное покрытие релевантных направлений в этом лимите; НДС и доли
кампаний задать явно. Карты локального профиля также учитывать в общем бюджете.
Правило одинаково для new/established; явное задание клиента приоритетно.
Для товарной части выбрать e-commerce v3 и подготовить product_source: URL-фид
из задания либо источник по сайту с разметкой через интерфейс. Дождаться DONE
с товарами; после создания — PROCESSED у каждого ShoppingAd/ListingAd. Проверить
карточки, цены, изображения, ссылки и выборку фильтра в интерфейсе.
Контракт: `direct://kb/product-campaigns`.

## Шаг 0. Собрать до любых действий

Сайт/посадочные, объект продвижения, география, бюджет и сроки, цель кампании и KPI (CPL/CPA/ДРР), номер счётчика Метрики и список целей, доступ на редактирование счётчика, юнит-экономика (средний чек, маржинальность, допустимая доля рекламных расходов), сезонность и расписание, минус-слова, семантика, тексты и УТП, коллтрекинг при телефонных заказах.

Для конверсионной стратегии нужны проверенные счётчик и цели; историю не требовать. Экономику использовать для оценки результата — см. «Метрика, цели и ценность конверсии» (`direct://kb/metrika-goals`).

## Структура аккаунта

- Подготовлен `semantic_plan`: направления бизнеса, источники с датами и регионами,
  разбор доступной истории, выбранные/исключённые/ожидающие кандидаты с причинами.
- Каждая группа имеет `semantic`: намерение, предложение, посадочную, причину
  разделения, брендовый сегмент и источники ключей. Полная схема и ориентиры:
  `direct://kb/structure-semantics`. Не дополнять семантику ради количественной нормы.
- **Поиск и РСЯ — всегда разные кампании.** Разная логика фраз, ставок и объявлений.
- Кампании группируются по целям и стратегиям, а не «всё в одну».
- Ретаргетинг — отдельные группы или кампании без других таргетингов в той же группе.
- Принцип 2026 года: не «запустить рекламу», а **разделить спрос, посадочные, цели и сценарии оптимизации**. Так проще увидеть, какие кампании реально дают лиды.
- Все фразы группы ведут на одну посадочную страницу; посадочная релевантна запросу и адаптирована под мобильные.

## Настройки кампании

- При конверсионной стратегии указаны счётчик Метрики и целевые действия;
  при «Оптимизации конверсий» — проверены счётчик и цели; история не обязательна.
  Для «Максимума кликов» счётчик и цели необязательны; их отсутствие не блокирует настройку.
- Недельный бюджет ≥ 20 × целевая цена конверсии.
- При ручном управлении заданы собственные цели; при оптимизации кликов задана максимальная цена клика.
- Включён мониторинг сайта (остановка при неработающем сайте).
- **Отключено автоматическое применение рекомендаций Директа.**
- Заблокированы показы в мобильных приложениях и внешних сетях (AdsNative, BidSwitch и др.).
- Минус-фразы проверены по бизнесу и посадочной; общего обязательного списка нет. Заданы расписание показов и регионы.
- Дополнение «Промоакция» добавлено только при наличии действующей акции,
  применимой к рекламируемому предложению и доступной для выбранного формата.
  Проверены условия, сроки, страница акции (если задана) и сохранённая настройка.
  Если подходящей акции нет, отметить «не применимо»; это не недостаток настройки.
- При использовании организации из Яндекс Бизнеса проверены её карточка и
  контактные данные. В API объявления проверен бизнес-профиль (`BusinessId`)
  по ожидаемым `business_profiles`; привязка организации на уровне кампании
  проверяется отдельно. Не объединять эти объекты под названием «визитка»:
  устаревший `VCardId` не используется в нашем контракте ЕПК. Наличие `BusinessId`
  само по себе не доказывает привязку организации к кампании или конкретное место показа.
  См. `direct://kb/api-contract`.

  Источники: [Промоакция](https://yandex.ru/support/direct/ru/efficiency/promotion),
  [бизнес-профили Businesses.get](https://yandex.ru/dev/direct/doc/ru/businesses/get),
  [переход на ЕПК](https://yandex.ru/dev/direct/doc/ru/unified-campaign-update).
- UTM-разметка задана на уровне кампании (`TrackingParams`) и попадает во все ссылки.
- Всегда проверить итоговые URL с этой разметкой, а не только исходные Href.
  Подставить тестовые значения динамических параметров, сохранить yclid, проверить
  основные и быстрые ссылки GET-запросом с desktop/mobile User-Agent, редиректы и
  содержимое на soft-404. Ошибка, неизвестный параметр или неполная проверка — BLOCK.
  `landing_pages_verified=true` не заменяет такую HTTP-проверку.
  Для названия кампании использовать `yd_campaign_name={campaign_name}`:
  `name` конфликтует со служебным параметром WordPress и может вызвать 404.

## Настройки групп

- Регион показа корректен на уровне группы.
- **Поиск:** точные фразы, релевантные объявлениям; вопрос автотаргетинга решён осознанно (см. «Автотаргетинг, корректировки, ретаргетинг» (`direct://kb/targeting-adjustments`)).
- **РСЯ:** у каждой группы есть условие показа: ключи, явно выбранный автотаргетинг, интересы или ретаргетинг. Группы интересов/ретаргетинга создаются отдельно.
- Корректировки ставок на старте не ставятся — сначала статистика.
- Узкие низкочастотные фразы объединены в одну группу, чтобы не поймать «Мало показов».

## Объявления

- В каждом `ResponsiveAd` подготовлены 3–7 уникальных заголовков и ровно 3
  уникальных текста; минимум 3 заголовка содержательно используют 45–56 знаков,
  `TextAd` и одиночные поля не используются.
- Новая группа Поиска, РСЯ или Карт содержит 1–3 комбинаторных объявления.
  Старт — одно полное объявление; дополнительные нужны для отдельных гипотез.
  При нескольких объявлениях у каждого задана своя `hypothesis`.
  Лимит Яндекса: 3 неархивных, 10 с архивными. Изображения и видео подбираются
  по месту показа. Перенесённые старые группы проверяются отдельно.
- Заполнены **все** дополнения: быстрые ссылки (минимум 4, предпочтительно 8), описания к ним, уточнения, цена, кнопка, контакты. Общий набор создаётся один раз; `sitelink_set_id` задаётся в шаблоне/кампании bundle, а компилятор подключает его к объявлениям. Отдельный набор нужен только при различии содержания.
- Ключевая фраза — в начале заголовка; в тексте — выгоды и УТП, а не общие слова.
- Точные посадочные под конкретный продукт/оффер, не главная.
- UTM-метки во всех ссылках, включая быстрые ссылки. Динамические параметры: `{campaign_id}`, `{campaign_name}`, `{gbid}`, `{ad_id}`, `{phrase_id}`, `{keyword}`, `{source}`, `{source_type}`, `{position_type}`, `{device_type}`, `{region_id}`, `{region_name}`, `{retargeting_id}`. В быстрых ссылках подстановка `{campaign_id}`, `{ad_id}`, `{banner_id}`, `{phrase_id}` гарантируется только если те же параметры есть в ссылке самого объявления.
- Объект продвижения назван конкретно — абстрактность это частая причина отклонения модерацией.

## Кнопка и варианты изображений

- Для каждого объявления РСЯ подготовлены или сгенерированы минимум 3 разных
  креатива (максимум 5). Все загружены и переданы в `ad_image_hashes` одного
  объявления. Повторы файлов и кадрирования одного изображения не заменяют
  разные креативы. После создания проверить все хэши через API и картинки в UI.
- В каждом объявлении с `href` выбран наиболее релевантный текст кнопки из
  доступных вариантов интерфейса и передан `action_button` с `text`, `reason`.
  `href` автоматически берётся основной; для страницы контактов явно передать
  `destination=contacts` и проверенный URL. Не оставлять ссылку в UI незаполненной.
- После создания сохранить кнопку через интерфейс и повторно открыть каждое
  объявление: сверить подпись, полный URL и переход. `Ads.get` кнопку не подтверждает.
  Пока `required_manual_actions` не выполнены, настройка не завершена.

## Перед нажатием «создать»

Проверить лимиты символов («Технические ограничения Директа» (`direct://kb/tech-limits`)), рабочие ссылки, соответствие фраз и текстов, бюджет и стратегию, регионы, даты. **Показы не включать автоматически** — сначала показать план человеку.

## После создания — карусель каждого объявления РСЯ

Всегда добавить отдельную «Карусель» из 2–10 релевантных фотографий клиента.
Обычные `AdImageHashes` не засчитываются. При отсутствии поддержки в API
сохранить через интерфейс и повторно открыть каждое объявление: проверить
число и порядок слайдов, сохранить свидетельство проверки по ID объявления.
Не завершать настройку с невыполненными `required_manual_actions`. Если браузер
недоступен, сохранить слайды и ID, явно сообщить о незавершённом этапе.
Требования к изображениям: `direct://kb/agency-policy`.

## После создания — клиентский отчёт

Независимо от способа создания (MCP, отдельный скрипт API или интерфейс),
сформировать клиентский отчёт по фактическим объектам и опубликовать в
`https://bi-data.ru/elama/<client_login>/create/`. Локальный preview недостаточен.
Завершение: `creation_report.status=published`, `creation_report.verified=true`,
HTTP 200 и совпадение SHA-256; в итоговом ответе дать публичную ссылку.
При отдельном скрипте явно вызвать этап публикации с параметрами из настройки
MCP. При пропущенном отчёте использовать существующие ID, не создавать дубли.
Подробности: `direct://kb/server-capabilities`.

См. также: «Плейбук донастройки» (`direct://kb/optimization-playbook`), «Возможности сервера» (`direct://kb/server-capabilities`), «Стратегии и бюджеты» (`direct://kb/strategies-budgets`)

## Клиентский отчёт после настройки

Создать или обновить единый отчёт Media Targeting на
`https://bi-data.ru/elama/<client_login>/`: в левом меню «Настройка» и «Статистика».
Настройка отражает фактические результаты; статистика добавляется позднее в этот
же документ с сохранением настройки и предыдущих периодов. Перед обновлением
прочитать существующий отчёт и модель, сохранить backup. Выгрузка `/create/`
не заменяет основной клиентский отчёт. Подробности: `direct://kb/client-report`.


## Приёмка после настройки

- Кнопка обязательна у объявления со ссылкой и изображением/видео; текстовый Поиск
  без медиа не получает обязательный ручной шаг по кнопке.
- Для Карт допустим опубликованный BusinessId без Href; связь организации проверяется
  на нужном уровне, не выводится из одного BusinessId объявления.
- Просмотрите сводку `api_warnings`, точные дубли ключей и предложения кросс-минусовки.
  Лексическое пересечение требует смысловой проверки; сервер не добавляет минусы автоматически.
- Модерация — отдельный явный шаг перед запуском. После неё и наступления StartDate
  показы могут начаться. Создание не даёт разрешения отправлять кампанию на модерацию
  или запускать её. В результате указан `launch.moderation` с ожиданием отдельной команды.
