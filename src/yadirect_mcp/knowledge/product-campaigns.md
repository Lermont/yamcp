# Товарная ЕПК: фид или сайт

## Сценарий

Для интернет-магазина стандартный тест — товарная ЕПК + отдельный Поиск.
Выбирайте `ecommerce_new_v2` либо `ecommerce_established_v2`. Старые `_v1`
сохранены. Канал `product` создаёт ЕПК с товарной галереей и РСЯ: недельный
бюджет задан в Search, Network использует NETWORK_DEFAULT и не получает второй
бюджет. Поисковая выдача и Карты в товарной кампании выключены. Обычный Поиск
создаётся отдельным `channels.search`. Общий client_budget включает обе кампании.

В товарной группе допустимы одно `ShoppingAd` и одно `ListingAd`, последнее —
если источник содержит подходящие страницы каталога. Комбинаторные объявления
остаются в Поиске/обычной РСЯ. Требование 3–5 собственных изображений и карусели
обычной РСЯ не переносится на объявления, генерируемые из товарного источника.
Ключи необязательны, автотаргетинг добавляется явно; реальные ключи при наличии
нужно обосновать в semantic_plan. Товарная группа также требует semantic:
направление, предложение, посадочная, источники и причина разделения.

## Выбор источника

1. Если URL фида указан в задании, в том числе отдельной строкой/сообщением,
   использовать именно его. Не подменять его главной сайта или догадкой `/feed.xml`.
   Сначала прочитать существующие фиды `direct_product_source(client_login)`.
2. Если такой URL уже есть у этого клиента, использовать его FeedId. Если нет,
   `direct_feed_create(client_login, feed={name, url})` даёт preview с полным
   хешем и одноразовым confirmation. Повтор с неизменными данными и confirmation
   использует MCP elicitation и durable job. `direct_write_job` читает результат.
   Создаётся RETAIL URL-фид. Обновление существующего фида этим инструментом
   не выполняется. Ошибка явного фида не разрешает молча перейти на сайт.
3. Если фид не предоставлен, использовать сайт при наличии товарной разметки.
   `direct_product_source(source={type: website, url, sample_urls})` проверяет
   разметку на 1–10 фактических страницах товаров и возвращает явный UI-шаг.
   Проверяются Schema.org Product в JSON-LD и microdata в полученном HTML;
   отсутствие в статическом HTML не доказывает отсутствие после JavaScript.
   В таком случае нужна проверка сайта/разметки; готовность автоматически не заявляется.
4. В интерфейсе Директа через Playwright выбрать создание источника по сайту,
   указать исходный сайт, сохранить, получить FeedId и повторно проверить
   привязку к сайту. Не отправлять HTML-адрес в Feeds.add как ссылку на XML-фид.
   Публичный Feeds.add описывает только URL/FILE; отдельного SITE-параметра нет.
5. Перед созданием кампании FeedId обязательно перечитывается через API под
   точным client_login. Нужны Status=DONE, NumberOfItems>0 и доступные поля
   TitleAndTextSources. Если созданный в UI источник API не возвращает, путь
   API блокируется: это незавершённая подготовка источника, а не готовая кампания.

Идентификатор, сайт и данные проверки источника входят в хеш плана. URL-фид
независимо сверяется по UrlFeed.Url; привязка источника website подтверждается
специалистом в интерфейсе и сохраняется как caller_reviewed. MCP не выдаёт это
за независимую API-проверку URL сайта.

## Фрагмент канала в bundle

Здесь URL и ID условные. Обязательные поля всего bundle и semantic_plan опущены.

```json
{
  "policy_name": "ecommerce_new_v2",
  "channels": {
    "product": {
      "weekly_budget": 3400,
      "product_source": {
        "type": "feed",
        "url": "https://example.com/feed.xml",
        "feed_id": "12345",
        "sample_urls": ["https://example.com/product/example"]
      },
      "groups": [{
        "name": "Категория товаров",
        "ads": [{
          "type": "shopping",
          "default_text": "Выбирайте товары в каталоге. Доставка и гарантия.",
          "feed_filter_conditions": [{
            "Operand": "categoryId", "Operator": "EQUALS_ANY", "Arguments": ["10"]
          }]
        }]
      }]
    }
  }
}
```

Входные поля объявления: `type=shopping/listing`, `default_text`, опциональные
`feed_filter_conditions`, `title_sources`, `text_sources`, `sitelink_set_id`,
`ad_extension_ids`, `business_id`, `hypothesis`. FeedId берётся из источника
канала. Фильтры передаются в нативном формате Operand/Operator/Arguments:
не более 30, общий JSON до 65 КБ. Семантическую совместимость фильтров со схемой
конкретного фида и фактический набор товаров проверяют при подготовке и в UI.
Поля заголовков и текстов дополнительно сверяются с живым TitleAndTextSources.
Отсутствие фильтров означает все предложения источника.

Для сайта product_source выглядит так:

```json
{
  "type": "website",
  "url": "https://example.com/",
  "feed_id": "67890",
  "sample_urls": ["https://example.com/product/example"],
  "site_feed_verified": true,
  "review_reason": "Источник создан по этому сайту; URL и FeedId сверены в интерфейсе"
}
```

Нельзя выдумывать FeedId, результат проверки сайта или review_reason.
Фид асинхронно обрабатывается Яндексом: успешное Feeds.add и даже успешная
сверка его параметров не означают, что его уже можно использовать в кампании.

## Приёмка

Preflight повторно проверяет источник, доступ к фиду и образцы конечных URL с
кампанийными метками на desktop/mobile. Это выборка, не проверка всех URL фида.
После создания readback независимо сверяет тип объявления, FeedId, фильтры,
источники текстов/заголовков, текст по умолчанию, дополнения и места показа.
`FeedProcessingStatus=PROCESSED` обязателен: UNKNOWN/UNPROCESSED/EMPTY_RESULT
не дают подтверждённой готовности. Повторная проверка — `direct_verify_job`,
не повторное создание. Фид перечитывается и после создания кампании.

`product.generated_offers` остаётся обязательной проверкой реальных товаров,
цен, наличия, изображений и ссылок после фильтра в интерфейсе. Формальное
совпадение payload не подтверждает состав предложений. Запуск показов требует
отдельной команды. При неизвестном исходе записи сохраняется журнал/блокировка;
автоматически повторять создание фида или всей кампании нельзя.
