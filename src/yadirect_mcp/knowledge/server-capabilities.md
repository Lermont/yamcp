# Возможности сервера и границы автоматизации

## Бизнес-профили — 18.09.2026

Поддержаны шесть профилей v1, два товарных e-commerce v2 и неизменная legacy-политика
1.12.0. Профили управляют проверками целей/контактов, структурой, списком
исключений, общим бюджетом и выбором двух поддержанных стратегий по объявленным
проверенным данным. Источники статистики автоматически не загружаются;
содержание проверяет специалист. Readback применяет исходный профиль.
В e-commerce v2 поддержаны ShoppingAd/ListingAd, фильтры, товарная галерея +
сети с общим бюджетом, проверка источника и обработки. direct_feed_create
создаёт URL-фид; источник по сайту с разметкой создаётся через интерфейс,
затем проверяется его доступность API. CRR/MaxProfit не добавлены.
Текущие planning_defaults: Поиск + РСЯ; для магазина — товарная + Поиск;
ориентир 30 000 RUB в месяц на создаваемый план.
Контракты: `direct://kb/policy-profiles`, `direct://kb/product-campaigns`.

## Измерение и проверки новых планов — 18.09.2026

Политика 1.12.0 добавляет стандартный `utm_v1` с сохранением BI-параметров,
явное отключение автотекстов, общий `client_budget` только для кампаний плана
и сверку ожидаемых `business_profiles` до и после записи. Лимит включает все
варианты, учитывает валюту и явно заданную ставку НДС. Месячный бюджет переводится
в средний недельный × 12/52; жёсткий календарный лимит не реализован.
`GoalId=13` поддержан как выбор реальных PriorityGoals с минимум одной целью
кроме 12. Пропуск общего лимита в старых данных — not_configured; старые
сохранённые планы без новых полей не приобретают эти проверки автоматически.
Подробный контракт: `direct://kb/tool-reference`.

## Подготовка и применение после аудита 11.09.2026

Недостающие сведения, включая бюджет, выяснить в начале задачи. Затем
самостоятельно подготовить и проверить полный план и назначение отчёта.
Перед записью MCP-клиент запрашивает согласие через elicitation на конкретный
логин и полный хеш плана. `confirmation` остаётся техническим одноразовым токеном
целостности и сам по себе не разрешает запись. Решение, хеш, время и имя клиента
сохраняются в журнале. Участие человека обеспечивает доверенный интерфейс клиента;
сервер фиксирует `client_attested`, а не удостоверенную личность человека.

Запуск и возобновление показов требуют отдельной явной команды пользователя.
Preview, live preflight, независимый readback, резервные копии и проверки
публикации сохраняются. `BLOCK`, неполные выборки и дубли останавливают запись.
Разрешения среды исполнения и границы доступа это правило не изменяет.

## Браузер: Playwright

По прямому указанию пользователя от 11.09.2026 все действия с браузером выполнять
через Playwright с установленным Chrome, включая карусели РСЯ, кнопки,
загрузку фотографий и визуальную проверку клиентских отчётов. Использовать
отдельный авторизованный профиль; не трогать чужие профили и процессы.
CUA и браузерный плагин не использовать вместо Playwright без новой явной просьбы
пользователя. После сохранения заново открыть объект, сверить ID, содержимое,
ссылки, количество и порядок слайдов, загрузку изображений и отсутствие ошибок.
API остаётся доступен для поддерживаемых операций; это правило выбирает способ
управления браузером; отдельная команда по-прежнему нужна для запуска рекламы.

## Возрастные ограничения и интересы аудитории — политика 1.9.0

`age_min` принимает 0, 18, 25, 35, 45, 55; `age_max` — 17, 24, 34, 44, 54 или
null (без верхнего ограничения). Границы должны совпадать с возрастными группами
API. Например, `age_min:25, age_max:54` создаёт −100% для AGE_0_17, AGE_18_24,
AGE_55. Независимый readback сверяет все исключения. Ответ BidModifiers.add
содержит массив `Ids`; исполнитель сохраняет и учитывает каждую корректировку.

Интересы необязательны и выбираются для конкретной кампании. MCP не задаёт
отраслевые аудитории по умолчанию: названия и ID интересов хранятся в клиентском
плане. Если `audience_interest_ids` отсутствует, условия по интересам не создаются.

В группе РСЯ можно указать `audience_interest_ids` (1–10 уникальных ID из
Dictionaries.AudienceInterests, только SHORT_TERM) и `audience_priority`
(LOW/NORMAL/HIGH, по умолчанию NORMAL). Такие группы отдельные: без ключей,
автотаргетинга и offer_retargeting. Долгосрочные и ANY интересы в этом варианте
ЕПК не поддерживаются. До подтверждения preflight проверяет ID и длительность
по живому каталогу и показывает названия интересов.

Исполнитель создаёт RetargetingList типа AUDIENCE с одним правилом ANY,
затем привязывает AudienceTarget к созданной группе. Он не использует InterestId
для мобильных приложений. ID обоих объектов сохраняются при частичной ошибке;
повторять весь пакет нельзя. Readback проверяет группу, ID, интересы, приоритет,
доступность и отсутствие параллельных ключей. Усечённые ответы не считаются успехом.

Источники, проверено 09.09.2026:
[Возрастные корректировки](https://yandex.ru/dev/direct/doc/ru/bidmodifiers/add),
[RetargetingLists.add](https://yandex.ru/dev/direct/doc/ru/retargetinglists/add),
[AudienceTargets.add](https://yandex.ru/dev/direct/doc/ru/audiencetargets/add),
[Интересы в ЕПК](https://yandex.ru/support/direct/ru/products-text-image-ads/user-profile).


Этот документ сверяет регламент настройки с тем, что MCP физически проверяет и
применяет. Он не подменяет официальный контракт Direct API.

## Проверка рекламных URL — политика 1.8.1

Live preflight перед preview и перед созданием, readback и аудит проверяют
конечные URL с эффективной разметкой, включая быстрые ссылки и yclid, с
desktop/mobile User-Agent. Приоритет полного блока: объявление > группа >
кампания; выбранный блок переопределяет одноимённые значения в Href.
ID до создания и неизвестные на момент проверки значения ключа, площадки,
региона — репрезентативные тестовые значения, не перебор всех будущих кликов.
После создания используются фактические ID и названия кампаний.
Если в интерфейсе заданы отдельные параметры объявления, которые текущий
публичный ads.get не возвращает, агент отдельно сверяет их в интерфейсе;
нельзя объявлять такие UI-only настройки проверенными по одному API-снимку.

Каждый набор быстрых ссылок читается один раз. За одну проверку выполняется не
более 150 уникальных GET на устройство; остальные URL явно остаются непроверенными
и блокируют положительный итог. Таймауты, ошибки, неизвестные динамические параметры
и soft-404 не считаются PASS. Проверки сохраняют защиту от SSRF и ограничение HTML.
`include_landing_pages=false` не подтверждает работоспособность ссылок.
Профиль разметки использует `yd_campaign_name`, а не конфликтующий с WordPress `name`.

## Основной сценарий

- `direct_policy` отдаёт версию `agency_default_v1`, источники, хеши снимков и
  модель `PASS / WARNING / BLOCK / MANUAL`.
- `direct_campaign_settings`, `direct_adgroups`, `direct_ads`, `direct_keywords`
  и `direct_goal_catalog` читают фактические настройки, группы, объявления,
  ключи, полный профиль автотаргетинга, посадочные и цели.
- `direct_campaign_audit` читает кабинет, сохраняет полный JSON и возвращает сводку.
  Локальная запись отражена в readOnlyHint=false. Детали читает direct_read_artifact.
- `direct_report` согласует конверсионные цели и атрибуцию с текущими настройками
  кампаний либо с явными параметрами сравнения. Без общего набора целей/модели
  требуется разделение по CampaignId. Метаданные с периодом, НДС и предупреждениями
  сохраняются рядом с TSV и возвращаются при `direct_read_report`.
- `direct_campaign_plan` компилирует `direct_campaign_bundle_v1` в отдельные
  нативные `UnifiedCampaign` для Поиска, РСЯ и условных Карт. Write API не
  вызывается.
- `direct_campaign_apply` работает только при `YD_MODE=campaign_setup`.
  Первый вызов делает live preflight и выдаёт одноразовое подтверждение,
  связанное с логином и SHA-256 точного плана. Второй создаёт объекты через v501.

После создания сервер повторно читает кампании, группы, объявления и ключевые
фразы, сравнивает их с планом, запускает policy-аудит и проверяет, что кампании
не активны. `resume` не вызывается. Неуспешный readback меняет результат на
`complete_unverified`, а частичная запись — на `partial`; известные ID при этом
не теряются.

Низкоуровневый результат преобразуется во вспомогательный HTML настройки с кампаниями и их
настройками, группами, географией и автотаргетингом, ключевыми фразами и полным
набором объявлений. В нём нет внутреннего сравнения «план / факт» и списка
расхождений: они остаются в техническом JSON-аудите. Клиентская версия
рассчитана на неспециалиста: API enum и сырые JSON-блоки не выводятся, стратегии,
места показов и автотаргетинг описываются терминами интерфейса Директа. В
комбинаторных объявлениях варианты заголовков и текстов показываются отдельно с
пояснением, что Директ выбирает подходящую комбинацию для каждого показа.
Локальный путь:
`<YD_OUT_DIR>/<client_login>/create/index.html`. При заданном
`YD_CREATE_REPORT_SSH_HOST` и явно заданных remote root/public base URL файл публикуется как
`<YD_CREATE_REPORT_PUBLIC_BASE_URL>/<client_login>/create/` через backup,
временный файл и атомарный `mv`. `creation_report.verified=true` выставляется
только после HTTP-проверки SHA-256. Если ни одна кампания не создана, публичная
версия не обновляется.


## Единый отчёт обязателен независимо от способа создания

Канонический клиентский отчёт —
`https://bi-data.ru/elama/<client_login>/`. Он создаётся при настройке,
затем дополняется статистикой по тому же адресу с сохранением настройки и
предыдущих периодов. В левом меню — «Настройка» и «Статистика».
Контакты и полный порядок: `direct://kb/client-report`.

Правило распространяется на `direct_campaign_apply`, отдельный скрипт SDK/API
и интерфейс. Автоматический обработчик `creation_report` пока публикует только
вспомогательную выгрузку `/create/`; агент использует её для сверки фактических
объектов и явно собирает или обновляет единый отчёт по каноническому адресу.
Публикация `/create/` и `creation_report.verified=true` сами по себе не означают,
что единый клиентский отчёт готов. `direct_report` отдаёт статистические TSV,
но не сливает их с клиентским HTML автоматически.

Перед обновлением прочитать текущую страницу и исходную модель, сохранить backup.
После проверки атомарно заменить основной `index.html`; проверить
HTTP 200, SHA-256, оба раздела в браузере и сохранность прошлых данных. В итоговом
ответе дать каноническую ссылку. Локальный preview не заменяет публикацию.

Отдельный скрипт может не наследовать `YD_CREATE_REPORT_*` из конфигурации MCP;
назначение публикации и параметры SSH передаются явно. Внутренние журналы и
JSON-аудиты не публикуются. Ошибку публикации нельзя молча заменить локальной
ссылкой или объявить этап завершённым. Для восстановления перечитать существующие
кампании по известным ID и собрать отчёт, не создавая кампании повторно.

## Карусель РСЯ обязательна

Во всех объявлениях РСЯ добавляется отдельная «Карусель» из 2–10 изображений.
Публичный Direct API не предоставляет её поля. `AdImageHashes` — варианты
обычного изображения, они не создают и не подтверждают карусель. Компилятор
возвращает `required_manual_actions` с индексами объявлений, исполнитель —
с фактическими ID созданных объектов. Эти действия выполняются после API-записи
через интерфейс, включая сценарии отдельных скриптов и донастройки.

`status=complete` и `api_creation_complete=true` подтверждают только создание
объектов через API, не выполнение карусели. Аудит выдаёт `network.carousel=MANUAL`.
После сохранения повторно открыть каждое объявление и зафиксировать число и
порядок слайдов, ID объявления и свидетельство проверки интерфейса. Не объявлять
настройку завершённой до выполнения действий. При недоступности интерфейса
сохранить ID и фотографии для продолжения, явно сообщить о незавершённом этапе.
После добавления обновить клиентский отчёт и проверить публикацию; подготовленные,
но не сохранённые слайды не выдавать за действующее дополнение.
Подробные ограничения изображений и источники: `direct://kb/agency-policy`.

## Правила компилятора

Компилятор технически допускает Поиск без РСЯ при явно выбранном ином составе;
стандартный тест услуг/B2B и локального бизнеса включает оба канала.
Поиск и РСЯ физически разделены. Для явных
различий значение канала может быть массивом вариантов. Когда две или больше
кампаний отличаются только каналом или настройками, общие `groups` задаются один
раз в `campaign_template`, а `campaign_variants` меняют только `channel`,
`name`/`name_suffix`, `region_ids`, `weekly_budget`, `budget_approved` и
`strategy`. Компилятор разворачивает шаблон до валидации и SHA-256; вариант не
может менять группы, объявления или ключи. Карты добавляются только при
`office=true`. Недельный бюджет обязателен либо
берётся из `YD_DEFAULT_WEEKLY_BUDGET` как технический fallback. В новых планах
доли задаются явно в пределах client_budget, общий лимит приоритетен.
Диапазон 2 000–5 000 RUB относится только к legacy-профилю;
`budget_approved` сохранён для совместимости.

Для `maximum_clicks` счётчик и бизнес-цели необязательны: `counter_ids` и
`priority_goals` можно опустить или передать пустыми массивами. Компилятор
не отправляет пустые `CounterIds`/`PriorityGoals` и не подставляет фиктивную
цель. Если цели не выбраны, `goals_reviewed`, каталог целей и
`allow_unverified_goals` не требуются. Счётчик без выбранных целей допустим.
Если бизнес-цели указаны, сохраняются проверка счётчика, ручное подтверждение
целей и live-проверка каталога. Для `maximum_conversion_rate` по-прежнему
обязательны счётчик и явный `goal_id` из `priority_goals` либо селектор 13
при наличии хотя бы одной приоритетной цели кроме системной 12.

Основание: [UnifiedCampaign.add](https://yandex.ru/dev/direct/doc/ru/campaigns/add-unified-campaign):
`CounterIds` необязателен, `WB_MAXIMUM_CLICKS` не требует `GoalId` или
`PriorityGoals`. Проверено 09.09.2026.

Доступны `maximum_clicks` и `maximum_conversion_rate`. Обе ограничивают расход
недельным бюджетом; вторая требует явный `goal_id` из `priority_goals` либо
селектор 13 с бизнес-целями и не задаёт среднюю CPA. Цели — выбранные специалистом бизнес-действия с отдельной
ценностью, а не автоматическое «все зелёные».

TrackingParams всегда ставятся на кампанию. Поиск получает минус-фразы по
`negative_keyword_policy`: по умолчанию custom без автоматического списка,
отраслевой профиль выбирается явно, исключения и дополнения содержат причину.
Снимок 249 фраз доступен только как `legacy_reviewed`. Пересечения с бизнесом,
текстами и ключами требуют рассмотрения. Отсутствие старого списка не блокирует
аудит. Автотаргетинг обязателен с явными Exact/Narrow без расширенных категорий
и брендов конкурентов; РСЯ получает снимок исключённых площадок.
В группе Поиска/обычной РСЯ 1–3 ResponsiveAd; одно полное объявление — допустимый старт.
Для product действуют отдельные правила: не более одного ShoppingAd и одного ListingAd.

`age_min` обязателен; значение 18 создаёт кампанийную корректировку AGE_0_17 со
значением 0. По умолчанию и при `schedule: "always_on"` используется штатное
«Круглосуточно»: при создании `TimeTargeting` не передаётся. Не заполняй все
168 часов и отдельные часы праздников ради 24/7, в том числе в отдельных
скриптах создания. Ограниченное расписание передаётся явно через
`Schedule.Items`: строки из номера дня и 24 коэффициентов, а не объекты
`Days`/`Hours`. Неуказанный день API считает включённым на 100%.
Источник: [Campaigns.add](https://yandex.ru/dev/direct/doc/ru/campaigns/add).
До выдачи
подтверждения preflight запускает Вордстат по географии каждой группы Поиска/Карт.
Одинаковые пары фраза/география переиспользуются в текущей проверке; географии
разных групп не объединяются. Отсутствующий каталог целей можно обойти только явным
`allow_unverified_goals=true`.

Политика 1.6.0 требует в новых типизированных планах `semantic_plan` и `semantic`
групп: источники, направления, решения по кандидатам, историю и причины разделения.
Без них план не готов к записи. Источники остаются `provided_in_bundle`: сервер
проверяет контракт, но не заявляет их самостоятельное чтение. Нормы количества —
объяснимые ориентиры; технические пределы обязательны. `summary.keywords` больше
не включает автотаргетинг; для всех объектов Keywords.add есть `summary.criteria`.
Схема и пример: `direct://kb/structure-semantics`.

География задаётся и проверяется на уровне регионов групп.

## Ручные границы

Direct API не сообщает цвет и дату создания целей и не доказывает наличие
физического офиса. Поэтому `goals_reviewed` при выбранных целях, `office`, `regions_verified`,
`landing_pages_verified` задаются явно. При наличии
старой кампании `goal_catalog_campaign_id` позволяет preflight сверить выбранные
ID с `GetStatGoals`. Если проверить выбранные цели невозможно, preflight
блокирует запись без явного `allow_unverified_goals=true`; это исключение
отображается как `WARNING`. Для максимума кликов без выбранных целей
проверка каталога не требуется.

Наборы быстрых ссылок и уточнения создаёт отдельный защищённый инструмент
`direct_ad_assets_create`. В `ResponsiveAd` можно передать полученные или уже
существующие `sitelink_set_id`, `ad_extension_ids`,
`ad_image_hashes` и `video_extension_ids`. Для совместимости принимается также
одиночный `ad_image_hash`. Отсутствие обязательных для внутреннего чек-листа
элементов становится `WARNING` или `BLOCK`. Узкие обновления существующих
кампаний выполняет `direct_campaign_repair`; он не запускает показы и отдельно
перечитывает изменённые поля.

Набор быстрых ссылок должен содержать минимум 4, предпочтительно 8 ссылок.
Общий `sitelink_set_id` задаётся один раз в bundle, шаблоне кампаний, канале или
группе; объявление может его переопределить. Компилятор разворачивает ID в API-поля
объявлений. Preflight и ремонт проверяют содержимое набора перед записью; аудит
читает каждый уникальный набор один раз и проверяет реальное количество ссылок.

Для комбинаторного объявления обязательны нативные массивы из 3–7 уникальных
`titles` и ровно 3 уникальных `texts`; минимум 3 заголовка должны содержательно
использовать 45–56 знаков. Одиночные поля `title`/`title2`/`text` отклоняются. Посадка задаётся `href` либо `business_id`; зависимые от ссылки
`display_url_path` и `sitelink_set_id` без `href` блокируются до API. Executor
режет `Campaigns.add` по 10 объектов, а группы, объявления и ключевые фразы —
по 1000 согласно лимитам методов. `api_units_estimate` в preview показывает
прогноз только для успешных add-вызовов; preflight, readback, ошибки и отдельное
создание дополнений туда не входят. После live preflight прогноз сравнивается с
остатком из `Units`: при нехватке write-фаза блокируется до пополнения, выбора
баллов агентства или подтверждённого ручного копирования через Директ
Коммандер с последующим API-аудитом. После write-операции `units_usage`
содержит фактический расход и журнал ответов `Units` по запросам этой
операции.

## Legacy raw-инструмент

`direct_campaign_setup` удалён из MCP. Доступный путь создания ЕПК —
`direct_campaign_plan` → `direct_campaign_apply`; оба инструмента публикуются
только в `YD_MODE=campaign_setup`. Частичный apply сохраняет созданные ID,
но автоматическое продолжение отсутствует: дочерние объекты добавляются после
ручной сверки в интерфейсе/Коммандере. Повтор всего bundle не является восстановлением.

Подробная миграция: `direct://kb/migration-v03`.

## Регулярные клиентские отчёты — политика 1.8.0

`direct_client_report` собирает статистику и единый HTML локально кодом.
Для агента выдаётся ограниченный `brief`; `write_insight` сохраняет только
вывод по версии данных. CLI `python -m yadirect_mcp.report_runner refresh-all`
обрабатывает явно зарегистрированных клиентов без LLM API, с дневным кешем
и остановкой после финальной выгрузки окна. Расписание и публикация не
включаются автоматически. Схемы и ограничения — `direct://kb/client-report`.


## Кнопка и изображения РСЯ — политика 1.11.0

`ads[].action_button`: объект с `text` (наиболее релевантная подпись из доступных
в UI), `reason` (обоснование), `destination` (`main` по умолчанию либо `contacts`),
`href`. Для `main` URL подставляется из `ads[].href`; для `contacts` нужен явный
проверенный URL контактов на том же сайте. Кнопка обязательна при наличии `href` и изображения или видео.
Для текстового Поиска без медиа она необязательна. Это метаданные для UI, в API `ResponsiveAd` они не отправляются.
Preflight проверяет URL кнопки с метками на desktop и mobile. После создания
агент сохраняет кнопку в интерфейсе и повторно открывает объявление для проверки
текста и URL; API-аудит оставляет `ads.action_button=MANUAL`.

В каждом объявлении РСЯ нужны **3–5 разных изображений**: подготовьте или
сгенерируйте минимум 3 самостоятельных креатива, загрузите все через
`direct_ad_assets_create(images)` и передайте `ad_image_hashes` одного объявления.
Один хэш и дубли не проходят план. `direct_ads` возвращает `ad_image_hashes` и
`image_count`, readback сверяет весь набор с планом. Генерацию выполняет агент
инструментом изображений или в интерфейсе, сам сервер изображения не генерирует.
Карусель остаётся отдельным требованием. `required_manual_actions` содержит
точный выбор кнопки и ID созданных объявлений; `setup_complete=false`, пока есть
обязательные UI-действия. Полный порядок: `direct://kb/agency-policy`.


## Изменения протокола после аудита 11.09.2026

`direct_write_job(client_login, job_id)` читает результат фонового preview/apply.
При `running` повторите чтение через `poll_after_seconds`; оно не возобновляет запись.
Write-тулы дополнительно требуют согласия через MCP elicitation. ID во всех JSON
возвращаются строками. Журнал сохраняет каждый write-запрос и ответ, неизвестный
исход удерживает блокировку логина. Полный контракт, кеш, порядок сверки, новые
поля цены/ЕРИР/IP/минус-наборов/ретаргетинга: `direct://kb/api-contract`.

`direct_list_clients(limit=1000, offset=0, include_archived=false)` возвращает
`truncated` и `next_offset`; продолжайте страницы до `truncated=false`. Поля
баланса этот инструмент не получает. При `include_archived=true` включает архивных.
