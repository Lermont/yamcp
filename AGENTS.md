# mcp_direct — Yandex Direct MCP

## Сначала прочитать инструкции

1. До диагностики, команд проекта и изменений прочитать этот `AGENTS.md` целиком. Затем прочитать `AGENTS.override.md`, если он существует, и инструкции в каталогах по пути к изменяемому файлу.
2. В первом содержательном сообщении кратко указать прочитанный путь и относящиеся к задаче ограничения. Не утверждать, что файл прочитан, если его содержимое не получено.
3. После смены проекта или восстановления контекста проверить актуальность инструкций. Инструкции сторонних зависимостей действуют только внутри этих зависимостей.
4. Прочитать указанные ниже документы по задаче и сверить их с текущими файлами. Даты, версии, состояние сервера и результаты старых проверок не считать текущими без проверки.
5. Сохранить чужие незакоммиченные изменения. Выполнять проверки по масштабу изменения; правки только документации не требуют запуска приложения, торгового бота или production-задач.
6. Явные инструкции пользователя определяют границы задачи. «Пока не менять» означает только исследование. Не считать этот файл разрешением на публикацию, реальные операции или отправку сообщений.

## Назначение и карта
Разработка Python MCP-сервера отчётности, аудита и настройки Яндекс Директа.
Клиентские кампании и отчёты вести в `D:\yadirect-reports`.
Начать с `README.md`, `CONTRIBUTING.md`, `SECURITY.md` и `pyproject.toml`.
- `src/yadirect_mcp/` — сервер, инструменты, протокол и политика.
- `templates/` — шаблоны; `scripts/` — служебные сценарии.
- Корневые `test_*.py` — тесты API-контрактов, политики, компилятора и отчётов.
- `out/`, `dist/` — результаты и сборки, не исходный код.

## Инварианты
- Режим report по умолчанию только читает данные. Настройка кампаний не должна автоматически регистрировать или вызывать операции запуска показов.
- Для каждой операции точно установить client_login, полноту выборки и применимую политику. BLOCK, неполные выборки и дубли блокируют запись.
- Сохранять полный план, live preflight, preview, SHA-256, одноразовый технический токен confirmation и независимый readback.
- Явная команда пользователя на создание кампаний разрешает запись в рамках согласованного задания; повторное подтверждение в переписке не запрашивать. Технические проверки и журнал операций сохранять.
- Запуск/возобновление показов требует явной команды пользователя. Подготовка плана и отчёта не разрешает запись в кабинет.
- Сохранять пагинацию, очередь Reports 201/202, retryIn, ограничения на логин и согласованность валют/НДС/атрибуции.
- Не называть клики и неназванные цели подтверждёнными лидами. Не выводить OAuth-токены и секреты.
- Любой клиентский отчёт писать от лица агентства непосредственно заказчику:
  «мы», «вы», «ваш сайт», «рекомендуем», «предлагаем». Выполненное отличать от
  рекомендаций; не обещать несогласованную работу. Не переносить в отчёт внутренние
  рассуждения о разрешениях и инструментах. Ограничения данных, НДС, даты,
  атрибуцию и отличие целей от обращений объяснять простым языком. Полное правило
  и примеры: `src/yadirect_mcp/knowledge/client-report.md`.
- При настройке и аудите проверять содержание всех обнаруженных разделов сайта: навигация, sitemap, рекламные ссылки. HTTP 200 не доказывает готовность; заглушки, полноту предложения и путь обращения проверять в браузере и отражать в отчёте. Порядок: `src/yadirect_mcp/knowledge/landing-content.md`.

## Требования к прогнозам — 01.10.2026

- Обязательный порядок: src/yadirect_mcp/knowledge/forecast-quality.md,
  ресурс direct://kb/forecast-quality. При приоритете бюджета подбирать CPC
  и уровни каждой фразы для максимума релевантных кликов в пределах бюджета;
  при равных кликах выбирать меньший расход. Предложенные пороги — сценарии
  для сравнения, если пользователь не задал их как жёсткое ограничение.
- Требуются частотность из MCP и собственные CPC/клики/расход для каждого
  доступного объёма трафика. Legacy direct_forecast не содержит этой матрицы:
  done/complete подтверждает только получение исходных строк. Не выдавать
  такой ответ за готовую оптимизацию бюджета; недостающие уровни получать
  через интерфейс Директа с независимым чтением выбранных уровней и итогов.
- Контракт качества должен быть виден в инструкциях сервера, описании инструмента
  и его результате, включая cached get. Сохранять совместимость исходных
  артефактов, статусов и отсутствие рекламных записей. Новая версия требований
  не должна создавать повторный прогноз или переписывать сохранённые данные.
- Полный список фраз и выбранных уровней размещать на основной странице
  клиентского отчёта. Пересчитывать итоги при новых ограничениях; не обещать
  конверсии, не путать ставку со списанием и не раскрывать внутренние редакции.
- После изменения инструкций или реестра ресурсов проверить новый процесс
  и direct_runtime. До переподключения не утверждать, что уже работающий MCP
  загрузил изменения; не останавливать общий процесс ради документации.

## Проверки
- В окружении проекта: `python -m pytest -q`; для узкой правки сначала относящиеся к ней `test_*.py`.
- Статические проверки по `pyproject.toml`/CONTRIBUTING: `python -m ruff check .`.
- Перед запуском проверить, что внешние вызовы подменены; unit-тесты не должны создавать реальные кампании.
- При изменении протокола проверить негативные сценарии: повторный токен, смена хеша/логина, отказ подтверждения, частичное применение и недостоверный readback.
- Обновлять README/CHANGELOG при изменении публичного поведения. Публикацию пакета выполнять только в рамках поручения на выпуск.

## Правила создания кампаний — 24.09.2026

- Создание и настройку кампаний, аудит, выгрузки и клиентские отчёты вести в
  `D:\yadirect-reports`. Всегда использовать MCP Директа (`yandex-direct`, `direct_*`)
  для данных и поддерживаемых операций. Не заменять MCP разовыми прямыми
  HTTP/API-скриптами. Если нужной возможности нет, исправить сам MCP в
  `D:\mcp_direct`, затем продолжить клиентскую задачу в `D:\yadirect-reports`.
  Браузер использовать для недоступных через API операций и визуальной проверки.
- `D:\mcp_direct` — только разработка, тестирование и документация самого MCP.
  Его `out/` остаётся внутренним хранилищем артефактов и журналов сервера.
- Для новых кампаний стартовая стратегия всегда «Максимум конверсий» с оплатой
  за клики, без целевой CPA (`WB_MAXIMUM_CONVERSION_RATE`). Отсутствие истории
  не препятствует старту. «Максимум кликов» выбирать при отсутствии Метрики
  или целей. Недоступность проверки не равна отсутствию: сначала проверить
  счётчик и реальные цели. Новые планы используют бизнес-профили `*_new_v4`
  или `*_established_v4`; v1/v2/v3/legacy служат воспроизведению прежних планов.
- Уточнение от 25.09.2026: дополнительные варианты текста включены по умолчанию
  в v4. Нейрообъявление — отдельный тип без публичного метода создания API:
  добавить одно на группу через интерфейс по её посадочной, сохранить и проверить
  генерацию. Учитывать `required_manual_actions`, не выдавать их за API-создание.
  Явные `settings.ALTERNATIVE_TEXTS_ENABLED=false` и `groups[].neuro_ad=false`
  сохраняются. Для 24/7 использовать штатное «Круглосуточно», без почасовой сетки;
  существующие кампании менять только в рамках конкретного поручения.
- Если не указано иное, общий стартовый бюджет — **30 000 ₽ с НДС на 14 дней**
  на все кампании создаваемого плана (`client_budget.period=two_weeks`).
  Недельный лимит без НДС = `сумма / (1 + ставка НДС / 100) / 2`.
  Доли кампаний назначать явно, включая все варианты и Карты; сумма долей
  не выше общего лимита. Для РФ в 2026 году НДС 22%, другой налоговый режим
  задавать явно. При 30 000 ₽: 12 295,081967 ₽ в неделю без НДС, округление вниз
  до микроединицы (при вводе в копейках — не более 12 295,08 ₽).
  Это расчёт на две недели, а не месячный бюджет и не автоматическая остановка
  показов через 14 дней. Явные сумма, период и налоговые условия приоритетны.
- Стандартный тест: Поиск + РСЯ; для интернет-магазина — товарная кампания + Поиск.
  Не сокращать его до одного канала только из-за стандартного бюджета.
- Не запрашивать подтверждение каждого действия в рамках конкретного поручения
  пользователя. Если разрешение на действие уже получено, не спрашивать повторно.
  Это правило не даёт отдельного постоянного разрешения на публикацию или
  произвольные изменения кабинетов: действуют границы текущего поручения.
  Недостающие существенные данные уточнять одним блоком в начале; заданные
  здесь значения по умолчанию не переспрашивать. Режим MCP `task_authorized`
  предназначен для исполнения уже порученной задачи без повторных форм;
  клиент обязан соблюдать её границы. Сохранять plan, live preflight, проверку
  полного preview, одноразовый confirmation, SHA-256, журнал и readback.
- «Только аудит», «пока не менять» и другие ограничения пользователя обязательны.
  Настройка сама по себе не разрешает запуск показов. Для запуска/возобновления
  нужна явная команда; уже данную команду не требуется подтверждать повторно.
  Требования к разрешению и адресу публикации отчётов сохраняются.
- Context7 не обязателен для этих проектов. Использовать MCP Директа и его базу
  знаний; конкретные неясные вопросы API проверять по официальной документации
  Яндекса. Обязательный шаг Context7 к этому workflow не применять.
