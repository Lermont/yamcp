# Переход на официальный MCP Python SDK v2

На 02.10.2026 актуальный стабильный официальный релиз — 2.2.0 (07.09.2026).
Поддерживаемый диапазон `mcp>=2.2.0,<3`; нижняя граница проверяется отдельно в CI.
Это пакет `mcp`, не самостоятельный пакет `fastmcp`.

Источники: [релиз](https://github.com/modelcontextprotocol/python-sdk/releases/tag/v2.2.0),
[миграция](https://github.com/modelcontextprotocol/python-sdk/blob/v2.2.0/docs/migration.md),
[многошаговый ввод](https://github.com/modelcontextprotocol/python-sdk/blob/v2.2.0/docs/handlers/multi-round-trip.md).

## Совместимость

- `MCPServer` заменяет `FastMCP`; внутренние SDK Settings не изменяются.
  SDK v2 сам не читает `.env`. Жизненный цикл закрывает собственный DirectClient,
  импорт сохраняет конфигурацию логирования вызывающего приложения.
- Имена инструментов, входные схемы и аннотации, ресурсы `direct://kb` и
  `direct://kb/{doc}`, wire-поля результатов сохранены. Python-атрибуты SDK —
  snake_case; собственная сериализация протокольных моделей использует `by_alias=True`.
- Протокол 2025-11-25 сохраняет форму через обратный запрос. В 2026-07-28
  обработчик возвращает `InputRequiredResult`; SDK `Client` выполняет продолжение.
  Прямой `ClientSession.call_tool` требует явного управления этим циклом.
- Изучены `Resolve/Elicit`. Здесь выбран документированный ручной возврат
  `InputRequiredResult`: он позволяет оставить согласование в существующей точке
  после нормализации/проверки плана, не переносить бизнес-логику в граф зависимостей
  и сохранять собственные структурированные коды отказа. Два механизма не смешиваются.
- До ответа фоновые apply jobs не создаются. При продолжении повторяются только
  проверки до согласования; после него остаются live preflight, блокировка логина,
  журнал запросов/ответов и readback. Частичное применение не повторяется автоматически.
- SDK защищает состояние продолжения процессным ключом и связывает его с вызовом.
  Реестр хранит nonce, вопрос, операцию, логин, хеш и утверждение клиента.
  Исходный TTL 30 минут не продлевается. Отказ/отмена освобождает резервирование;
  старое состояние не подходит для нового запроса формы. Пропавший клиент оставляет
  резервирование до TTL; новый preview выдаёт отдельный токен.
- Отсутствие capabilities, URL-only elicitation и неизвестные имя/версия клиента
  блокируют форму. `task_authorized` включается только конфигурацией владельца,
  не является fallback и сохраняет `task_scope_delegated` в журнале.
- Собственные jobs, статусы и артефакты не мигрируются в SDK tasks. Требования
  к прогнозу не меняются. Обновление SDK само по себе не улучшает прогнозы или скорость.
- `scripts/local_mcp_session.py` использует `Client`, 600 секунд на запрос и cwd
  из конфигурации. Он неинтерактивный, без callback согласия: форм elicitation не подтверждает.

## Изолированная подготовка

Не используйте venv запущенного общего MCP. Создайте отдельный checkout нужного
коммита и в нём новое окружение (Windows; на Linux путь `bin/python`):

```powershell
py -3.11 -m venv .venv-sdk-v2
.venv-sdk-v2/Scripts/python.exe -m pip install -e ".[dev]" "mcp==2.2.0"
.venv-sdk-v2/Scripts/python.exe -m pytest -q
.venv-sdk-v2/Scripts/python.exe -m ruff check .
.venv-sdk-v2/Scripts/python.exe -m build
.venv-sdk-v2/Scripts/python.exe -m twine check dist/*
```

Тесты используют заглушки. Не запускайте `local_mcp_session.py` для проверки
миграции: он намеренно читает конфигурацию реального `yandex-direct`.
Сравнение каталога v1/v2 выполнялось в отдельных процессах: одинаковые 23/33
инструмента в report/campaign_setup, их полные схемы/аннотации и ресурсы.
`direct_runtime.dependencies.mcp` показывает SDK именно запущенного процесса.

## Приёмка в Codex/Claude перед переключением

Автоматические проверки покрывают настоящий stdio двух отдельных процессов,
обе версии протокола, каталог/ресурсы, structured success/error, отказ/отмену,
повтор/конкуренцию confirmation, подмену состояния/аргументов и отсутствие capability.
Они не подтверждают показ форм в конкретных версиях Codex/Claude.

1. Оставьте существующий `yandex-direct` и его окружение без изменений.
   В отдельном тестовом профиле клиента зарегистрируйте только временный сервер
   `yadirect-sdk-v2-acceptance`: Python нового venv и абсолютный путь к
   `scripts/sdk_v2_acceptance_server.py`. Секреты и переменные `YD_*` не нужны.
2. Скрипт содержит только локальные демонстрационные инструменты и использует
   настоящий реестр согласования проекта. Он не импортирует DirectClient и не
   выполняет HTTP, SSH, публикацию или рекламные операции.
3. Запишите версию клиента. Вызовите `migration_preview`, затем `migration_apply`
   с возвращённой фразой. Проверьте, что форма показывает логин `demo`, полный
   хеш и операцию. Откажитесь, затем отмените новый вызов: счётчик записей должен
   остаться 0. Примите следующую форму с approve=true: счётчик становится 1.
4. Повторите фразу: ожидается ошибка без изменения счётчика. Проверьте
   `migration_status` и версию SDK. Отключите временную регистрацию.
   Клиент без поддержки форм должен возвращать отказ, а не разрешение.
5. Только после отдельной команды на переключение общего MCP укажите новый
   checkout/venv, сохранив прежние env и каталог артефактов. Старые preview-токены
   не переносятся: нужен свежий preview. Проверьте `direct_runtime`, режим report,
   каталог и ресурс forecast-quality в новом процессе.

В рамках подготовки PR общий MCP не переключался. Интерфейсная приёмка
Codex/Claude остаётся отдельным шагом перед эксплуатацией.

## Откат

Сохраните прежние checkout, venv и команду запуска SDK v1 до переключения.
Исходная база миграции: `6c6b8b78c2d80af71d3f88fd9f36978c1285ebde`.
При проблеме верните клиенту прежнюю команду/путь и после согласования перезапустите
только этот MCP. Не понижайте зависимости внутри нового venv и не меняйте исходники
работающего процесса. Журналы `out/jobs`, артефакты и lock-файлы сохраняются.
Прочитайте незавершённые jobs и выполните независимую сверку перед любым новым
планом; откат SDK не отменяет уже выполненные внешние операции и не разрешает повтор.
Все старые токены и состояния продолжения после перезапуска недействительны.
